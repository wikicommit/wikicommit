# Pass 4: Source Integrity Review (Review Subagent)

## Contents

1. What the review subagent is given — and nothing else
2. Check the returned `rules_version` against `.wikicommit/review-rules.md`
3. Route the cross-page findings
4. FAIL → regenerate, up to `generate.max_retries`
5. Retry limit exceeded → `failed_pages`, and what a human may do about it
6. Write the pages that passed; record the review
7. Update this source's management file `status`
8. Move to the next source

**The review discipline itself is not in this file** — it is in `.wikicommit/review-rules.md`, shared with `/wikicommit-review` and `/wikicommit-synthesize`. What stays here is the choreography: how the subagent is launched, what to hand it (step 1), and what to do with what comes back.

**Stamp `--pass pass4-review` on entry**, with `--source` naming this source's management file (under `--regenerate`, the page being rebuilt). **Pass `--token 7b06f4ce` with it** — the value of this file's `pass_token`. `record_run.py` opens this file itself to compare, so the stamp records that this file was read rather than that the pass was improvised; without `--token` the stamp reads `token: unchecked`.

For each generated page (content is carried as context from Pass 3):

**If `.wikicommit/review-rules.md` does not exist, stop the whole run and say so.** Do not review without it and do not fall back to a looser check. A review that never read those rules degrades to "does the page match the source" — losing evidence binding, the attribution checks, source-vs-source disagreement, cross-page contradiction and the rest — and **its output looks completely normal**. Since step 6 writes a record asserting that a review happened, a silent degradation would additionally be recorded as one. This is an installation problem, not a defect in any page, so it must not touch `failed_pages` or any source management file's `status`: tell the user to run `/wikicommit-init --no-overwrite` to install the file, and stop (the same treatment guard C gives a missing extraction package).

**The check itself is at the start of the run, in `SKILL.md`**, because discovering the missing file here would throw away a whole batch of fetching, extraction and generation. This restatement covers a run that somehow arrived here anyway: stop, exactly as above.

1. Launch a subagent and give it exactly these five things, and nothing else:

   1. **The path label `generate-pass4`**, stated as the path this review is running on. The rules file scopes several checks by path ("a check that does not name your path is not yours to run") and has a section per path, so a subagent left to guess which one it is on may skip the cross-page check the one-hop pages below were assembled for, or follow the `review-skill` section's "report findings; do not decide" and return no verdict for step 3/4 to route.
   2. **The page under review**, as generated by Pass 3.
   3. **The full extracted text of each of the page's sources**, each wrapped in a block marked `SOURCE` — the whole text Pass 1 extracted, not a summary of it and not the passages you consider relevant.
   4. **The existing pages one WikiLink hop away** (assembled as below), marked as context rather than `SOURCE`.
   5. **`.wikicommit/review-rules.md`**, with an instruction to follow it.

   **Do not include anything else.** Not Pass 2a's `summary`, not Pass 2c's analysis JSON, not your reasoning for how you wrote the page, and not the findings of a previous review round. You are the agent that wrote this page, and all of that is your own reading of the sources — handing it over makes the review agree with you exactly where your reading was wrong. The evidence-binding rule cannot catch this on its own: a summary is not world knowledge, so it slips past a rule about world knowledge while being just as much not-the-source.

   Passing the **full** extracted text rather than an excerpt is the same point in a different place. Choosing which passages the reviewer sees means showing it only the evidence you wrote from, which biases the review toward PASS by construction.

   **Assembling the one-hop pages**: run the script — do not search for them yourself.

   ```bash
   python .wikicommit/scripts/build_onehop_context.py --page-path "$(cat <<'EOF'
   <the page's repo-relative path>
   EOF
   )" <<'PAGE'
   <the page exactly as Pass 3 generated it, frontmatter included>
   PAGE
   ```

   It prints one `PAGE: <path> (outbound|inbound)` line per neighbour, then a `SUMMARY:` line. Read each path in full and pass the pages as context. The page body goes on **stdin**, and `--page-path` is used only to identify lang/Type/slug — the script never opens that path, because at this point the page is not on disk yet (`action: create`) or still holds its previous version (`action: update`), and reading it would return the links of a version that is not the one under review. `<Type>` and `<slug>` come from Pass 2's reading of a source and are validated nowhere, hence the heredoc form.

   The script applies the whole rule, so nothing here is left for you to reproduce: cross-language fallback, the three skips (`index.md`, which `rebuild_index.py` fills with every page's own WikiLink and which states no facts of its own; `status: removed` pages; and a translation of the page under review, where a disagreement is translation staleness that `check_translation_status.py` already reports as `STALE`), outbound-first dedup, and the cap of 5.

   **An empty result is a normal answer**, not a failure: `SUMMARY: outbound=0, inbound=0` means this page has no neighbours yet. Check that a `SUMMARY:` line was printed at all — its absence means the script did not run, which is a different thing entirely.

   Do not replace the script with your own regex: an improvised one easily misses this wiki's kebab-case slugs, and the failure is silent, because a smaller set looks exactly like a smaller neighbourhood.

   Two limits, both accepted rather than solved here. Within a batch, a page only ever sees siblings generated **before** it, so a pair may be checked from one side only or not at all; and a contradiction between pages generated in **different** batches is out of reach entirely, since neither run ever sees the other's page as new. A repository-wide sweep is the answer to both and is deliberately not built here.

2. **Check that the returned JSON carries `rules_version`, and that it matches the value in `.wikicommit/review-rules.md`'s frontmatter.** A missing or mismatched value means the subagent did not read the rules, and its verdict then says nothing about the checks those rules define — a PASS from an unread rulebook is indistinguishable from a real one, which is the whole reason for the echo.

   Relaunch the review **once**. If the second attempt is also missing or wrong, **stop the entire run and report it** — close the run record with `record_run.py end <path> --halted-reason "rules_version mismatch"` first, because this stops without changing a file, so nothing else records that it happened — do not consume `generate.max_retries`, do not add the page to `failed_pages`, and do not write `status: failed`. Nothing is wrong with the page: this is a problem with the instructions or the environment, and recording it against the page would leave a false record, which is worse than none.

3. **Route the cross-page findings the rules produce.** An entry with `page_at_fault: "other"` is not a FAIL — so when it is the only kind of defect found, `result` is `"PASS"` and step 6 writes the page normally. Do not regenerate, and do not touch the other page: Pass 4 regenerates one page against its own sources and has neither the other page's sources nor any mandate over it. Once the page's review has settled as a pass and step 6 has written it, append the pair — both page paths, the fact, and both versions — to a running list for the Completion Notice, the same way `ambiguous` / `exclude` / `failed_pages` are rolled up. Append it then rather than on each review attempt, so a retry driven by some *other* defect does not report the same pair twice, and a page discarded at step 5 is not reported as one this run generated.
4. If the review result is **FAIL** (for any of the above reasons), regenerate the page (up to `generate.max_retries` times from `.wikicommit/config.yml`; default: 2). **Feed the subagent's findings into the retry**: pass the full `issues` array from step 1 — most importantly each entry's `instruction` — back into the Pass 3 regeneration prompt as explicit, itemized corrections for this attempt, alongside the same source text and context Pass 3 used originally. Do not regenerate from a bare "the previous attempt failed review" instruction with no detail — a retry that never sees what was wrong repeats the same defect. Leave out the cross-page findings that point at the *other* page (`page_at_fault: "other"` — step 3's routing rule): regenerating this page cannot fix them, and feeding them in as corrections would push it away from what its own sources say.

   **Harvest the `MISSING_SOURCE` entries from every review round** — before each retry, and also on the final round that exhausts the retry budget and sends the page to step 5, which has no retry after it but still names the document the roll-up below must report as coming from a discarded page. Each entry names a document the page cited that is not among its `sources` — and a retry is about to make that finding disappear, because the fix is to drop the claim, after which the page PASSes and nothing records which document was missing. That is a real registration candidate thrown away: the reviewer could only raise `MISSING_SOURCE` because the source text identified the document, so its URL or title is already in hand. Append it to a running list for the Completion Notice — the same pattern step 5 uses for `failed_pages` — with the document's URL if the source text gives one, otherwise the specific title it names, plus the page and source this came up on. **Skip an entry that identifies no specific document** (a claim traced only to "an earlier post" with neither URL nor title): there is nothing to register, and a line saying so would be noise on every run. Do not let this change any verdict — harvesting is a side effect of the finding, not a substitute for the FAIL.
5. If the retry limit is exceeded, add the page to `failed_pages` and skip writing it to disk. **A human running this interactively may override that** — `max_retries` exists to stop a page that will not converge, and each retry finding a *different* defect is not that: it is the review working. When the retries have been turning up new defects rather than the same one, and the page is otherwise substantial, say so and ask whether to try once more instead of discarding it. Do not extend on your own in a non-interactive run, and do not extend a page that keeps failing the same way. Also append this entity — its `title`, `type`, the source management file's path, and (for `action: update` entities) the pre-existing page's `existing_path`, which was left unchanged — to a running list, the same pattern Pass 2 already uses for `ambiguous`/`exclude` entities, so every such failure can be rolled up together in the Completion Notice (`references/completion-notice.md`); otherwise it reaches only the management file, invisible from the page and from this run's summary.

   **Record the review even though the page was discarded** — this is the record most worth having, because a page that was never written leaves nothing else behind but a `failed_pages` entry naming it. Run `record_review.py` as described in step 6 below, with `--result discarded` and the page path the entity *would* have had; add `--sources-from` once per source management file whose text this review used, since there is no page on disk to read `sources` off. `page_content_hash` comes out empty, which is how a record says the page was never written.
6. Write pages that **passed** review to the working directory. **Do not commit — leave the files as untracked/modified in `git status`.** Then, in one call, pass every page just written to:

   ```bash
   python .wikicommit/scripts/reset_review_on_content_change.py "$(cat <<'EOF'
   <page 1>
   EOF
   )" "$(cat <<'EOF'
   <page 2>
   EOF
   )"
   ```

   Repeat the `"$(cat <<'EOF' … EOF)"` argument once per page. It is the free-text-in-shell-argument form rather than a bare path because `<Type>` and `<slug>` are not validated anywhere in the pipeline, and both come out of Pass 2's reading of a source document.

   This is what actually settles `review_status` for `action: update` entities (Pass 3 step 3). It compares each page against `git show HEAD:` ignoring six bookkeeping fields (`generated_at`/`generated_by`/`generated_with`, `review_status`, `reviewed_by`, `sources`) and, when anything else differs, sets `review_status: pending` and drops `reviewed_by` — so a `reviewed` page whose prose this run rewrote goes back into the review queue, while one that only gained a source keeps its sign-off. `action: create` pages and pages not yet tracked at HEAD are reported as skipped and left alone; the script is safe to hand every written page. A `RESET:` line means that page needs review again, and the next `/wikicommit-merge` will open a tracking Issue for it (its scan looks for `pending`, so no change is needed there) — roll those pages up in the Completion Notice so the user knows which previously-reviewed pages this run sent back. Do not decide this yourself instead of running the script: the comparison is deliberately textual, because letting a judgment call decide whether human review is required is exactly what the trust ladder cannot afford.

   Then record each page's review verdict, once per page:

   ```bash
   python .wikicommit/scripts/record_review.py "$(cat <<'EOF'
   <page>
   EOF
   )" --kind ai --stage generate-pass4 \
     --model "<the model ID this run's runtime reports for itself>" \
     --skill-blob "$(git hash-object .wikicommit/review-rules.md)" \
     --attempts <how many review rounds this page took> --result pass --json - <<'JSON'
   <the review subagent's JSON for this page, with every round's issues merged into
    one `issues` array and each entry carrying the `round` it was raised in>
   JSON
   ```

   **Record every page, not only the ones that had findings.** The denominator is the point: without it, a run in which nothing went wrong and a run in which review never happened produce the same silence. A page that passed on the first attempt gets `--attempts 1 --result pass` and an empty `issues` array.

   **If the subagent returned an `observations` array, write it to a file and pass `--note-file`.** Those are the remarks it made while deciding PASS — the ones that are not defects and so never reach `issues`; without the note a page reviewed with a remark and one reviewed in silence are identical on disk. One line per observation, written with a quoted heredoc so nothing in the text is re-expanded by the shell:

   ```bash
   note=".wikicommit/.cache/review-notes/<lang>-<Type>-<slug>.txt"
   mkdir -p "$(dirname "$note")"
   cat > "$note" <<'NOTE'
   <one observation per line, verbatim from the subagent's `observations` array>
   NOTE
   ```

   Then add `--note-file "$note"` to the `record_review.py` call above. **Put the file under `.wikicommit/.cache/`** — it is gitignored, which is where this project's scratch files go; anywhere under `.wikicommit/review/` would be swept into the commit by `/wikicommit-merge`, which stages that directory whole, and a scratch file would then sit there looking like a review record.

   Do not put the text on the command line with `--note` — it is free-text a subagent wrote, and the same reason keeps Close comments off the command line elsewhere in this project. **When the array is absent or empty, pass neither flag**; an empty body is what a review with nothing to add should leave, and a placeholder would make every record look like it had something to say. These go to the prose body rather than into `issues` on purpose: the sampling list a person works from counts findings, and filling it with non-blocking remarks would change what that list means while its selection rule is still being measured.

   **Merge all rounds into the one `issues` array.** Each round of step 4 can find a different defect, and recording only the final round would give a page that failed once and was then fixed an empty `findings` list — erasing exactly the signal worth keeping. Tag each entry with the `round` it came from. `attempts` is passed separately because the last round may have found nothing at all.

   Pass the JSON through as it came back. The script drops `source_quote` itself, so there is nothing to strip by hand — and because it is the script that drops it, the guarantee does not depend on this instruction being followed. `page_content_hash` and `reviewed_sources` are computed by the script from the page on disk; do not try to supply them.

   `--skill-blob` records which version of the review instructions produced this verdict — the hash of `.wikicommit/review-rules.md`, which is where the discipline actually lives. `rules_version` and this hash are not redundant: the first is echoed by the subagent to prove it read the rules, the second is computed here to record which text judged the page, and a forgotten `rules_version` bump would make the first lie while the second stays true. If `git hash-object` fails, omit the flag rather than passing a placeholder: an absent value reads as "unknown", a made-up one reads as a version that never existed. **It fails only when the file cannot be read** — being untracked is not a failure, and neither is running outside a git repository; `git hash-object` returns the blob hash and exits 0 in both cases, so do not go looking for something to commit. The start-of-run check normally stops such a run long before this line; it stays for the race where the file disappears after that check.
7. Update the source management file's status locally (do not commit). This step only ever updates *this* source's own management file — a different, already-registered management file whose content happens to also be cited by a page this source's Pass 3/4 touched is deliberately left alone here and reconciled instead by the deterministic script in the "Ingest Status Reconciliation" step of `SKILL.md` — do not reconcile such files inline here, since a different file's correct status can depend on entities this source's Pass 2 never produced. Evaluate the following rules **in order** and apply the first one that matches (they are not independent conditions — later rules assume all earlier ones didn't match):

   **`failed_pages` is rewritten in full on every branch**, exactly like `ambiguous_entities` below: write this run's failures, and write `[]` when this run had none. A branch that leaves a previous run's list in place contradicts the status it just wrote, and the contradiction is not inert — `wikicommit-merge`'s generation-failure step keys on a non-empty `failed_pages` **regardless of `status`**, so a stale entry opens a tracking Issue naming a page this run never even attempted. That is the wrong record rather than a missing one, and it is also what would keep a source looking unfinished after the very change that finished it: a source whose only failing entity is no longer extracted at all reaches the first branch below, and the loop it was stuck in only visibly ends if the list it was stuck on is cleared with it.
   - Pass 2 returned no entities at all, or there are no `failed_pages`, no `ambiguous: true` entities, **and at least one entity's page was generated successfully** → `status: generated`, record `generated_pages` list and `last_generated_at`. Delete the `## Failure Reason` section if present — a stale reason left in place would contradict the current `status`. **Entities excluded by `theme` or `.wikicommit/entity-policy.md` do not keep a source out of this branch**: leaving out what this wiki decided not to write is the run completing as designed, not stopping partway, and `partial` would tell readers of the published source page that something was stuck. The exclusions stay on record in `## Generation Notes` and the Completion Notice, which Pass 2c writes independently of this step. The "at least one page" clause is what keeps an all-excluded source out of this branch and on the next one.
   - One or more entities exist, and **all** of them were `action: exclude` in Pass 2 → `status: excluded`, no `generated_pages` (the exclusion reasons are already recorded in `## Generation Notes` from Pass 2; the Pass 3/4 loops naturally have nothing to iterate over for this source). Delete `## Failure Reason` if present (same reasoning as above).
   - One or more entities exist, and **all** of them were `create`/`update` entities that were attempted and failed (no `ambiguous: true` entities, no `action: exclude` entities, zero successes) → `status: failed`. Write a reason to `## Failure Reason` (create it if absent, overwrite if present) summarizing which entities failed and why in one sentence each — e.g. `"3 of 3 entities failed source-integrity review after 2 retries each (hallucinated or unsupported claims). See the wikicommit-generate session output for the full per-claim review detail — that detail is agent-to-agent only and is not persisted here."` Write it in English regardless of `<primary_lang>` (as in `references/pass1-extract.md` and `references/pass3-generate.md`).
   - Anything else (one or more `ambiguous: true` entities regardless of success count, or some pages generated while others went to `failed_pages`, or failures mixed with exclusions and no success) → `status: partial`, record `generated_pages` and `failed_pages`, and `last_generated_at` (an ambiguous entity never had a page written, and a failed one can still succeed, so either keeps the source out of `generated`). Delete `## Failure Reason` if present (same reasoning as the `generated`/`excluded` branches — `partial` is not `failed`, so no failure reason should remain attached to it).
     - **If any entity came back `ambiguous: true`, also write `ambiguous_entities`**: a list of `{title, type, alternatives}` entries, one per ambiguous entity, taken from Pass 2c's analysis JSON. Rewrite it in full every time this branch is reached, and **remove the field entirely on any of the three branches above — and on this branch too when no entity came back `ambiguous: true`** — like `## Failure Reason`, it describes the run that just ended, and a stale copy would claim a source is waiting on a human who has already been. The `partial`-to-`partial` case is the one that is easy to miss and the only one that can strand a stale list: a source whose document changed can come back here with a mix of succeeded and failed entities and no ambiguity at all, which is exactly the branch that would otherwise leave the previous run's entry in place.

       This is the one deferral in this Skill that cannot be expressed by leaving `status` alone: the source really did produce pages, so it moves to `partial` whatever happens to the ambiguous entity. On a file written by this version, `partial` with an empty `failed_pages` means only the ambiguous case; on a file written by an older version it can also mean an exclusion, and the field is what tells the two apart and names the waiting entities: see the collection step in `references/pass1-extract.md` for why the source is still not collected automatically, and what does re-queue it.
8. Proceed to the next source management file. `index.md` is rebuilt once for all Type directories after all sources are processed (that step is in `SKILL.md`, after this Pass returns) — no per-source action needed here.
