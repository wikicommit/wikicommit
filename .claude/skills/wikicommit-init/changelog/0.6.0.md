## [0.6.0] - 2026-09-14

### Added

- **`/wikicommit-reconcile` — put sources back in the queue after a policy, type template or
  generation rule changed** (Issue #874). Six kinds of input decide what a page says, and three
  of them had no route to the pages they already produced: a policy (`theme`,
  `entity-policy.md`, `source-policy.md`), a type template, and a generation rule or version.
  All three are read in one place — Pass 2c — and the only entrances that run it open when a
  source's *content* changes.
  - The sharper half is turning a switch back **off**. A source left at `status: excluded` could
    not be reached by any existing command: `/wikicommit-generate <url>` re-fetches, finds the
    hash unchanged and reports "no change"; `/wikicommit-generate <path>` skips before Pass 1
    starts; the bare `/wikicommit-generate` does not collect `excluded` at all. **All three print
    a success message**, so the only way through was to open the management file and edit
    `status` by hand — and nothing told anyone to.
  - The Skill generates nothing. It reports what the selection covers, asks once, and writes
    `status: pending` to the management files; the next `/wikicommit-generate` picks them up
    through its existing collection rule. That is the shape `check_ingest_freshness.py` already
    has, generalized — and `wikicommit-generate` itself is unchanged.
  - It does not work out what changed: the person running it is the person who changed it, so a
    detector could only report a bit they already hold. One of `--source`, `--type` or `--all` is
    required; there is no default.
  - Requeuing does **not** re-fetch URL sources (`source.hash` is left alone, so Pass 1 finds the
    cache unchanged), and does **not** delete pages that the new policy now excludes — nothing in
    the generate path removes a page. Compare each management file's `## Generation Notes`
    exclusion list against the pages that still exist, and use `/wikicommit-remove`.

- **`.wikicommit/guides/` — how-to walkthroughs, installed into your own repository** (Issue #846).
  Some setup is a procedure a person follows once rather than something a Skill does, and this
  project had nowhere to put one: the only giscus walkthrough sat at the end of a 600-line agent
  instruction file which said of itself that it should be shown "when they ask for it", so there
  was nothing to point anyone at. These live under `.wikicommit/` rather than in the project's
  own design docs for one reason above all — **a change made there would never reach a wiki that
  is already installed**, while these are refreshed by every later `/wikicommit-init` and
  `/wikicommit-update`, with `check_distribution_freshness.py` reporting staleness in between.
  - Starts with one file, `enabling-comments.md`: turning on the giscus comment box, which is off
    by default and whose three prerequisites fail at read time rather than at build time — the
    site builds, the box simply does not work.
  - Written in English only. That is a deliberate exception to this project's own rule that a
    human-facing string follows the reader's language, and the file says so itself: a guide is a
    distributed file rather than text rendered on the spot, so following that rule would mean one
    template per language.
  - The giscus notes in `quartz.config.yaml` and in the `wikicommit-init` Skill are trimmed to
    match. The *procedure* moved to the guide; the *design decision* — why reactions are not
    wired to `review_status` — stays in the config file you are editing when you might undo it.

- **A guide for applying a changed entity policy to pages you already have** (Issue #867).
  `.wikicommit/entity-policy.md` is read only while a page is being generated, so flipping
  `exclude_living_persons` — or writing a category into the prose body, or loosening either back —
  changed what the next run produced and left everything already on disk untouched. The template
  said as much and pointed at `/wikicommit-remove`, but nothing said where to look first, so the
  person who flipped the switch was left to work out their own wiki.
  - `applying-entity-policy-to-existing-pages.md` is the second file on the guides shelf. Its core
    is one command — `/wikicommit-reconcile --all`, then `/wikicommit-generate` — and most of its
    length is what that command still leaves to a person: pages already written are never deleted
    by a generation run, a page the run does rewrite goes back to `pending` and loses the name of
    whoever read it, matching the exclusion list in `## Generation Notes` against the pages on disk
    is by hand (the list names entities by title, a title cannot be turned back into a slug, and
    the `generated_pages` list that would have named them outright is rewritten by the same run),
    the switch cannot reach a person who appears as an organization of one, an event's organizer or
    a story's character, and over-excluding is the easier mistake — one pilot ended up with zero
    `Person` pages, three historical figures included.
  - It also records why no health check reports this: the join would have no evidence on one side
    (every page under `Person/` would be a candidate), doing the right thing would not clear the
    finding for most pages, presenting every `Person` page as a candidate pushes toward the
    over-exclusion the policy file itself warns about, and a setting change is a single event
    rather than something a standing check is shaped for.
  - It ships to every wiki, not just `--quartz` ones, and the pointer to the guides shelf printed
    after `/wikicommit-init` is no longer gated on the Quartz variants — that gate existed only
    because the one guide then on the shelf was about a Quartz plugin.

- **`.wikicommit/schema-authoring.md` — how a type file is written, in one place** (Issue #886). Four
  paths add a `.wikicommit/schema/<Type>.md`, and all four held the entire procedure: 20,031 B of it,
  duplicated. What they actually differ on is the *judgment* — how strong the evidence has to be
  before proposing a type (one sentence of theme prose, a list of candidate titles, a source's full
  text, or a page that already exists), how approval is obtained, and which `provenance` value is
  stamped — and that is the part the design justifies having four of.
  - The drift this prevents had already happened once: the rule that every `granularity` bullet must
    survive YAML parsing as a plain string was added by editing the same paragraph into all four
    sites, and the next such rule would have been the same four edits again.
  - Distributed like `.wikicommit/review-rules.md`, with `update: overwrite`: this is WikiCommit's
    procedure rather than your prose, and a repository able to edit it could quietly change how its
    own types get defined.
  - Each path still carries three lines of its own — verify every property against the vocabulary,
    start one `granularity` rule with `Boundary —`, stamp your own `provenance` — so that skipping
    the read leaves thin guidance rather than none. It also keeps the "don't propose a type that
    already has a file" check, which stays out of the shared file: moving it there would mean reading
    the file on every judgment instead of only when a type is actually being written.
  - **A missing file rejects the candidate, not the run.** Unlike the review rules, which every run
    reaches, this file is reached only when a type is being added — and adding none is the normal
    outcome. The entity falls back to an installed type, which is what the no-candidate case does
    anyway, and `check_schema_coverage.py` reports the gap afterwards.
  - It carries no version field, unlike `review-rules.md`. That file's version works because a review
    subagent echoes it back and the orchestrator checks it; here the reader is the same agent, so an
    echo would be self-reported and verify nothing.

- **`check_schema_files.py` — the type files themselves are checked now** (Issue #889).
  `wikicommit-generate`'s own instructions said "Nothing validates a schema file", and that was
  accurate. Files under `.wikicommit/schema/` come from three origins — the distributed templates,
  a type a Skill wrote at runtime, and one written by hand — and CI could only ever reach the first.
  A schema file also cannot be repaired by any Skill afterwards, since the exception that lets one
  be written is add-only, so anything written in a broken shape stayed broken until a person opened
  the directory themselves.
  - Every tool this needed already existed: the vocabulary check verifies a property, the shared
    module resolves a type's ancestry, and something already read `provenance`. What was missing was
    anything that ran them over the files.
  - Reports a `properties:` key that is not in the vocabulary or not in the type's domain (the same
    check a page gets, which never ran against the template the page came from); a `granularity`
    bullet turned into a mapping by an unquoted `": "`; a bullet **truncated** by an unquoted space
    and `#`, which is the one failure nothing else can notice — YAML hands back the part before it
    as an ordinary string, so the rule looks fine and its second half is simply gone; a missing
    `Boundary` rule; a `provenance` outside the known set; a missing `base` or no `wikicommit:`
    block at all; a `type:` that disagrees with the path it sits at, or a type name that is in
    neither the path nor the vocabulary; and a custom type with no prose saying why no standard
    type fits.
  - **Measured on three real wikis before deciding what to report**: 0, 7 and 15 findings. The
    truncation case is not hypothetical — one of them had a rule that ran about 1,000 characters
    reaching its readers at 723, with the rest silently dropped, and that same template is already
    fixed upstream.
  - Because of that, the summary splits the count: findings on a `provenance: default` file mean the
    repository holds an *older copy* of a template rather than that anyone wrote it wrong, and their
    remedy is the upstream diff that `check_distribution_freshness.py` already reports. In the wiki
    with 15, thirteen were of that kind.
  - Not blocking, and deliberately not part of `/wikicommit-merge`'s quality gate: one malformed
    schema file would otherwise leave a repository unable to merge anything at all. A **missing**
    `provenance` is not reported either — its absence means "written before that field existed".
  - **A wiki that does not have it yet reads the copy in the Skill tree.** The file is
    `update: overwrite`, so it only arrives on the next init — every wiki initialized before it
    shipped is without it, which would have refused every type addition while the same bytes sat in
    the Skill tree that was running. The four paths now read
    `.claude/skills/wikicommit-init/scripts/templates/schema-authoring.md` in that case, the route
    `/wikicommit-update` already takes for a script an older repository lacks, and only give up when
    neither copy is readable.
  - The custom-type half of `/wikicommit-schema-propose` reads the `granularity` section too. Its
    own path skips the standard-type step entirely, and a custom type carries `granularity` exactly
    like a standard one — the property and file-format sections are the parts that do not apply,
    since they resolve names against a vocabulary a custom type is outside of.
  - `tests/test_schema_authoring_single_source.py` holds it in one place, the same way
    `tests/test_review_rules_single_source.py` holds the review rules: a copy pasted back into a
    SKILL.md breaks nothing at the time, which is exactly why a test has to notice.

- **An excluded entity's existing page is now named in the run's output** (Issue #876). Generation
  never removes a page — `/wikicommit-remove` is the only path that does — so an entity a run
  excludes today can have a page from an earlier run still standing and published. Nothing pointed
  at it: the exclusion notes recorded which *entity* was dropped, by title, and a page's file name
  is a language-neutral English slug whose derivation does not run backwards (a common noun is
  translated, an established spelling kept, otherwise romanized). On a wiki whose `primary_lang` is
  not English — the two where this policy has actually fired are Japanese and Italian — going from
  the title to the page meant grepping `title:` across the tree, for an answer the generating pass
  already had as a by-product of naming the entity.
  - The path appears in the completion notice, where a person decides what to do, and in the
    management file's `## Generation Notes`, which outlives the run's output. Both are additions to
    lines that were already being written; no new report block.
  - **It states a fact, not a verdict:** the page exists, and this run neither created nor updated
    it. That is the whole of what an exclusion establishes — a page can rest on several sources, and
    one of them ruling the entity out today says nothing about the others.
  - **Only entries excluded on the entity policy's own grounds point at `/wikicommit-remove`.** An
    entity that merely fell outside the wiki's subject is reported and left alone, and **nothing is
    removed automatically**: a policy decides what to create, not what to destroy, removal is
    irreversible, and choosing `removed_reason` is a person's judgment.
  - The field that carries the path is information only here. On a created or updated entity it makes
    page generation read the existing page into context; that step handles only those two cases, so an
    excluded entity's page is never opened, rewritten, or removed on the strength of it.
  - Regeneration does not report this, because it does not re-run entity extraction. The way a policy
    change reaches existing pages is `/wikicommit-reconcile`, which puts the sources back in the
    queue for an ordinary run.

- **`wikicommit-generate`'s completion notice and extraction routing table moved out of
  `SKILL.md`** (Issue #894). A Skill's entry file is loaded in full on every invocation, and two
  of its sections are not needed on every invocation: the completion notice (20,116 bytes, ~95%
  conditional branches) until a run is ending, and the extraction routing table (4,949 bytes)
  only by the pass that extracts. A run that stops at source registration, or one under
  `--regenerate`, was carrying both regardless. The entry file is now 826 lines / 159,998 bytes,
  down from 1,091 / 182,209.
  - **The amount read into a conversation does not go down**, and nothing here claims it does —
    `check_skill_md_lines.py`'s surface figure went *up* slightly (203,344 → 208,039 bytes), for
    the pointers and the two new files' preambles. What changes is that the entry file is no
    longer read whole every time.
  - **This is where context compaction actually bit.** A harness may re-attach only a Skill's
    opening after compacting, and the completion notice sat far outside that — so it vanished
    mid-run and nothing said so. A pointer survives where the section did not, **but only if the
    pointer is in the opening**: one placed at its point of use, near the tail, is cut by exactly
    the same cut. Both pointers are therefore in the processing-flow section at the top, and a
    test pins them there.
  - **The call that closes the run record moved with the notice, deliberately.** Left in the entry
    file, forgetting to read the notice would cost a report and nothing else, with nothing to say
    so. In the notice, forgetting it leaves the run record open and `/wikicommit-status` reports
    `INCOMPLETE_RUN:` — the run's own bookkeeping notices.
  - **The passes still accumulate what the notice renders.** The running lists (`ambiguous`
    entities, `exclude` decisions, `failed_pages`, newly added types, language mismatches) are
    built by instructions that did not move; only the rendering did.
  - The write-permission contract (`## Notes`) stays in the entry file: the half that has to
    survive a compaction ("performs no Git operations") is already in the opening line, and the
    other half is only exercisable from a pass that the same cut would have removed.

- **`--regenerate`'s procedure moved out of `wikicommit-generate/SKILL.md`, and the size guard now
  measures something that cannot be gamed by moving it** (Issue #887). `SKILL.md` is read in full on
  every invocation, and the two modes are mutually exclusive: an ordinary run never used a byte of
  the regeneration procedure, while a regeneration run never used the 40% of the file belonging to
  the other mode. The procedure is now in `regenerate.md` alongside it, with a branch and a read
  instruction left behind. `SKILL.md` went from 195,097 to 176,864 bytes.
  - **The Skill is not split.** Passes 1, 3 and 4 are shared with ordinary generation, which is why
    this was never a separate Skill and still is not. Splitting the *file* is different: the unit
    differs (page-driven rather than source-driven) and the modes are exclusive.
  - If that file cannot be read, the run **stops** rather than improvising. Unlike a shared data
    file whose absence merely thins the guidance, this one *is* the procedure.
  - **The size guard changed in the same release, because the move would otherwise have made it
    lie**: the same prose in two files measured as 1,063 lines instead of 1,129, and a line-only
    guard would have called that an improvement. There are now two figures — the **instruction
    surface** (every instruction `.md` in the Skill's directory, in bytes; default 40,000) and the
    **`SKILL.md` body** (lines and bytes; default 500 lines, Anthropic's guidance kept at its own
    value and unit). Read as a pair, `body ↓` with `surface →` means a Skill was split and
    `body ↓` with `surface ↓` means prose was removed — a distinction the old figure could not make.
  - The byte threshold comes from two directions that agree: roughly 10,000 tokens at about 4 bytes
    per token, and a 1.4x gap in the measured distribution (largest below 28,777 bytes, smallest
    above 41,223). **It is deliberately not tied to any harness's compaction window**, which belongs
    to one harness at one version.
  - Lines had become a poor proxy: `.md` density across these Skills runs 41–166 bytes per line, a
    4.0x spread, and one Skill sat at 75% of another's byte count while passing the line guard.
  - The surface figure does **not** distinguish "moved to another file" from "moved to another
    context" — a subagent's prompt never reaches the parent's context, but looks identical here — so
    a Skill that delegates measures higher than it costs. The caveat is written into the script
    rather than worked around, since nothing static can tell the two apart.
  - Two other Skill scanners were widened in the same change, for the same reason: the
    user-facing-vocabulary check and the hard-coded-Japanese check both read only `SKILL.md`, so the
    move silently took two fenced blocks and a file out of their scope. They now read every
    instruction `.md` in a Skill's directory.

- **`type: path` sources keep their extracted text, the same way `type: url` sources have since
  Issue #278** (Issue #885). Extracting a scanned PDF, an EPUB or a `.docx` turns a file WikiCommit
  cannot read into text, and that text was thrown away at the end of every run. Re-processing the
  same source — a `status: partial` file picked up again, `--regenerate`, an entity extracted
  later — re-ran the whole extraction. Nothing in either design made this asymmetric on purpose,
  and the expensive half was the one without a cache: an OCR pass costs more than a network round
  trip, and needs an optional Skill installed to run at all.
  - The cache lives at `.wikicommit/.cache/extract-path/`, mirroring the management file's path
    under `.wikicommit/source/path/` **including the trailing `.md`** — so `raw/paper.pdf.md` and
    `raw/paper.docx.md` stay distinct, inheriting the collision-freedom Issue #573 established at
    the management-file layer. Dropping and re-adding the extension would reopen that silent
    wrong-source one layer down, where nothing compares hashes.
  - It is a separate tree from the `type: url` scratch files rather than one shared tree, because
    one tree can collide: a url scratch path has the shape `example.com/article`, which a
    repository file of that name also produces. Merging them would have cost a one-time
    invalidation of every URL cache — a re-fetch of every URL source — for no gain.
  - `add_source.py --check-path-cache` decides validity and is read-only; `--path-cache-path`
    prints where an extraction belongs. **Neither touches `source.hash`, and nothing else may
    either.** For a `type: url` source that field holds the extracted text's hash, which is why
    `--write-hash` works on the scratch file there; for `type: path` it holds the **raw file's**
    hash, and it is the reference point `check_ingest_freshness.py` compares against the file on
    disk. Overwriting it with an extracted-text hash would leave freshness detection reporting "no
    change" for a changed file, for that source from then on.
  - **`.md` / `.txt` sources are deliberately not cached.** There the raw file *is* the extracted
    text, so a cache would be a byte-identical second copy — doubling disk for the category where
    sources run largest while removing no limitation.
  - The reader is `resolve_source_cache_path.py --type path`, and adding it is what keeps this from
    being a receptacle with nothing in it. It also removes a limitation `wikicommit-ask` had written
    down about itself: `--include-source` read the **raw** file for `type: path` sources, so a
    `.docx`/`.epub`/scanned image arrived as garbled bytes. With a cache present those now arrive as
    the text that was actually extracted; without one, the old fallback and the old limitation
    remain.
  - Two limits are inherited rather than new: a cache does not expire when the extraction *tool*
    changes version (the `type: url` scratch files have behaved this way since Issue #278), and the
    cache is gitignored, so a fresh clone extracts everything once.

### Changed

- **`/wikicommit-generate` and `/wikicommit-merge` now check that `.wikicommit/scripts/` is in
  step with the installed Skills** (Issue #930). The two halves of what WikiCommit installs are
  refreshed by different commands — `npx skills add` for `.claude/skills/`, `/wikicommit-update`
  for those scripts — so a repository can hold new instructions and older scripts.
  - The dangerous shape is not a crash. When a new option is passed, or a new script is called,
    the old copy fails loudly and the cause is obvious. When only the *inside* of an existing
    option changed, it can fail in a way that **names the wrong thing**: Issue #925 moved where
    `record_run.py --token` looks for a pass file, and an older copy writes `token: missing`
    against a run that read its instructions correctly — recording a correct pass as a failed one.
  - No new detector was written. `check_distribution_freshness.py` already byte-compares that
    tree, and it reports correctly even when it is itself the stale copy, because both sides of
    the comparison (the template and the classification list) live in the half that
    `npx skills add` refreshes. A script that embeds a specific expectation cannot diagnose its
    own staleness; a generic comparison against the template can.
  - Both Skills run the copy under `.claude/skills/`, **not** the one under
    `.wikicommit/scripts/` — the latter is the half that may be stale, and a detector shipped in
    the stale half is the bug it is looking for.
  - It **warns and carries on**; it never stops a run. Most skew is harmless, and nothing in the
    check can tell which differences bear on the run at hand. Only the third shape above would
    justify stopping, and that is exactly the one no machine can pick out.
  - `check_distribution_freshness.py` gained `--only <path>` to narrow the report to one entry.
    This is not for speed (the full check takes a fraction of a second) but for relevance: at the
    start of a run, stale `quartz-plugins/` or workflows are real but not actionable *now*, and a
    line the reader cannot act on is how a report teaches people to skip it. A `--only` value
    matching no entry warns rather than reporting a clean result — as does one naming an entry
    this script never compares, since both print the same clean `SUMMARY:` — and `--only`
    suppresses the `VERSION:` line, whose `synced` half lags behind on repositories that are
    genuinely in step. Both Skills report every `OUTDATED:` / `MISSING:` / `ORPHAN:` /
    `WARNING:` line rather than the `OUTDATED:` ones alone: reading only one of them would put
    the silent clean result back.
  - The `OUTDATED:` line for `.wikicommit/scripts` now says what being stale there costs, and
    stops there (Issue #935). It named `/wikicommit-update` at first, which is wrong at one of
    the six places that run this check and redundant at two more: three of them belong to
    `/wikicommit-update` itself, and the one in its last step runs *after* the update, so a
    line there reports that the update just made did not take — prescribing the command that
    has only now failed. The consequence holds at every call site; the remedy is what each
    Skill already says in context. Other payloads keep the plain wording — a stale
    `quartz-plugins/` means a stale published site, which is a different thing to say.

- **The five Skills a model can start on its own now say when to use them, not just what they
  do** (Issue #912). A `description` is the only thing a model matches a request against, and
  the official guidance's own observation is that models *under*trigger — so a description
  that reads like a feature list gets a Skill that never fires.
  - `wikicommit-ask`, `wikicommit-quiz`, `wikicommit-search`, `wikicommit-serve` and
    `wikicommit-status` now name the situations they are for, including the ones where nobody
    says the obvious keyword. `wikicommit-search` and `wikicommit-status` got the strongest
    wording: both look like something a model could do with `grep` instead, which is exactly
    the case the guidance says gets skipped.
  - **The other twelve are deliberately untouched.** They set `disable-model-invocation: true`
    and only start when a person types the command, so there is no trigger for a description
    to improve. That is not an oversight to be fixed later — a model has no business starting
    `/wikicommit-merge` on its own judgment.
  - `wikicommit-serve` is worded more narrowly than the rest, because it runs a real `npm`
    build rather than reading files.
  - **A `description` must not contain a colon followed by a space.** Frontmatter is unquoted,
    so YAML reads the rest of the line as a nested mapping and the whole block stops parsing —
    taking `name` with it. This is now checked in CI.

- **A non-interactive run now defers a human judgment instead of discarding it** (Issue #910). Runs
  driven by a subagent are non-interactive by definition, so every prompt in `/wikicommit-generate`
  resolved without anyone — and two of them resolved by throwing the source away.
  - **Guard A** (the low-density warning) marked the source `status: failed`. It is a text-shape
    heuristic: a link-dense government page and a statistics table look like an empty JS shell, and the
    saitama pilot had 4 of 8 genuine sources flagged. `status: failed` is then collected by nothing, so
    a 30-source batch could quietly lose a third of itself. It now leaves the source where the queue can
    still reach it — the `status` it already had, or `pending` when the run was a forced recheck and that
    status was one nothing collects — records why in a new `## Deferred Reason` section, and moves on.
    The source stays in the queue, so the next run with a person present asks.
  - **A Pass 2b type candidate** below the strict auto-approval bar was declined, which meant the
    entity got written under an ancestor type — and no Skill can reclassify a page afterwards. It now
    defers the same way. The strict bar itself is unchanged: a candidate that clears it is still added
    with no prompt.
  - **An entity whose type could not be determined** is the one case that cannot be expressed by leaving
    the status alone, because the source really did produce pages. It is recorded in a new
    `ambiguous_entities` field, so the wait outlives the run that found it and `/wikicommit-status`
    names it. The route out is `/wikicommit-reconcile`; re-collecting it automatically would only reach
    the same ambiguity again on every run.
  - **Deferring is not the same as failing, and not everything defers.** A known JS-shell domain, an
    unreadable extraction, a YouTube URL of the wrong shape — a person looking at those reaches the
    same verdict, so they still fail. Deferral is for the judgments where a person would answer.
  - Three prompts that never said what happens without an answer now do: a source conflicting with the
    wiki's policy is not registered, a queue over five sources takes the first five, and
    `/wikicommit-merge` stops on warnings rather than squash-merging what nobody saw.
  - **A failure in Pass 1 used to be reported nowhere.** `/wikicommit-merge`'s generation-failure Issue
    keyed on `failed_pages`, which only Pass 4 writes — so a source that failed before any page was
    attempted raised no Issue, and `/wikicommit-status` left it out of its tally *because* that Issue
    was supposed to exist. Both are fixed.
  - **Existing repositories are not migrated.** A source already at `status: failed` stays there until
    someone brings it back by hand. Not with `/wikicommit-reconcile` — that Skill skips `status: failed`
    on purpose, since a source that never got past extraction has nothing for Pass 2c to re-run. Name the
    source instead: `/wikicommit-generate <url>` forces a re-fetch of a failed `type: url` source, and a
    failed `type: path` source needs its `status` set back to `pending` before re-running.

- **Each of `wikicommit-generate`'s passes is now its own file, and `SKILL.md` is the map**
  (Issue #911). `SKILL.md` was 831 lines against a 500-line guideline, and every one of them
  loaded on every invocation — including the runs that stop at Step 0 and the ones that take
  `--regenerate` and use none of it.
  - Passes 1 through 4 moved to `references/pass1-extract.md`, `references/pass2b-type.md`,

  - Reference files over 20,000 bytes open with a table of contents. The Skill guidance names
    300 lines, but a line of this project's instruction prose runs 40-170 bytes, so a line

  - **The total amount of instruction did not go down** — it went up slightly, by the new

    read its first source.

- **Source nodes are now told apart from pages in the global graph, and a legend says what the
  shapes and colours mean** (Issue #841). Sources were drawn exactly like entity pages — and since
  the graph shows them by default, they are usually the largest group of nodes in it. The one
  distinction the graph did make (hollow circle = tag) was never explained anywhere.
  - **Shape carries the kind, colour carries the visit state.** Sources are squares, tags stay
    hollow circles, pages stay filled circles; which colour a node gets has not changed. Colour was
    not available for this — the theme offers two accents plus grey, all three already spoken for
    by current / visited / not visited, and in dark mode the two accents are near neighbours. Shape
    also survives colour blindness.
  - **The legend lives in the control bar** and covers both halves, because neither is guessable
    from the graph. Its swatches are drawn from the same theme colours in the same shapes, so the
    key cannot drift from what it explains. It is translated into all thirty locales.
  - **Types are deliberately not encoded.** Twenty of them would need twenty legend rows, and the
    type filter in the same bar is the right way to narrow to the ones you want.

- **The global graph's filter bar is no longer squeezed into a 10vh strip** (Issue #838). The bar
  and the graph were each positioned against the same centred rectangle by hand — one at
  `height: 80vh`, the other at `calc(50% - 40vh)` — so the bar got whatever was left above the
  graph, which on a 700px-tall window is 70px. A four-row multi-select and its caption already
  exceeded that, and the bar scrolled inside itself to cope.
  - A wrapper now holds both and defines that rectangle once; the bar takes the height its
    contents need and the graph takes the rest. Nothing about the graph rendering changed.
  - Multi-select lists may now show up to eight rows instead of four. A wiki with twenty types was
    being filtered through a four-row window — and raising this only helps now that the bar can
    grow.
  - Clicking the gap between the bar and the graph no longer closes the modal. Closing it from the
    backdrop, with Escape, or by clicking the graph icon again all work exactly as before.

- **Tag and source nodes the filter cut off from every page are dropped from the graph**
  (Issue #839). Language and type filters apply to entity nodes only, and that is deliberate — a
  tag bridging two languages has to survive being narrowed to one of them (Issue #584). But nothing
  then removed the tags and sources the narrowing had left pointing at nothing, so filtering a wiki
  down to one type left a cloud of disconnected points around the handful of pages being looked at.
  - The test is **how many links reach an entity page**, not the node's plain degree. Published
    source pages link to one another — the sources index, each directory index and the root index
    all point at them — and every one of those neighbours is itself a source, so a source node's
    degree never falls below 1 however hard the graph is filtered. Counting reachable pages measures
    what the design already says in words: a tag or a source exists only through a page.
  - A node is dropped only when it reached a page **before** the filter and reaches none after.
    Anything that reached nothing to begin with — a failed or excluded source, an orphan page — is
    left alone, because the graph must not quietly hide what `check_orphans.py` reports.
  - Entity nodes are never dropped: a page of the type you asked for having no links is not a reason
    to hide the page. The "Links per node" bounds still use the plain degree, that being the number
    the reader can actually see.

- **The graph's control bar has a surface of its own, and its toggles read as filled buttons**
  (Issue #840). The bar has to sit outside the graph container — the renderer empties that container
  on every draw — so with no background of its own it floated over whatever page had opened the
  modal, seen through a blur. A control sitting on a different backdrop every time does not read as
  a control.
  - It now takes the same three declarations the graph container already uses (background, border,
    radius), so the two read as one panel.
  - The checkboxes became native `<button>`s carrying `aria-pressed`. Tab, Space, Enter and the

    fill rather than a tick mark — an area large enough to read at 0.8rem. The `{field, sync}`

  - **Hover could not use the theme's tertiary colour.** Measured against the shipped themes it
    gives 2.53:1 in light and 6.76:1 in dark, because that colour is identical in both themes while
    the text colour flips; a relative `brightness(0.92)` gives 9.55:1 and 5.01:1. Checking only one
    theme would have let it through.

- **A policy file's worked example can no longer be applied as if you had written it**
  (Issue #844). `.wikicommit/source-policy.md` and `.wikicommit/entity-policy.md` ship with their
  whole body as a commented-out example, and "is this body still the example?" was decided by a
  sentence repeated in four places telling an agent to judge it. The shipped text is on disk, so
  there was never anything to judge — and the mistake it invited runs one way, since every line
  of both examples argues for *excluding* something. A wiki could quietly adopt "do not take in
  personal blogs" or "no pages about non-public figures" without anyone choosing them, and the
  only visible trace would be one fewer page.
  - `read_policy.py` now returns the prose, with the example and every other HTML comment
    removed, and the three places that read these files call it instead of reading the body.
  - The rule it applies — **an HTML comment is never policy** — does not depend on which version
    shipped the example, so **a wiki created before this needs no migration**: its body is a
    comment too.
  - If your policy ends up entirely inside a comment (the likely way being to edit the example in
    place without deleting the `<!--`), you are told that a policy inside a comment is not read.
    An example edited in place and one nobody touched are the same bytes on disk, so it is said
    as a possibility rather than asserted.
  - The frontmatter is untouched: `exclude_domains`, `index_only`, `rejected` and
    `exclude_living_persons` are still read where they are applied.

- **`/wikicommit-init` now asks whether to skip pages about living individuals** (Issue #837). The
  entity-extraction pass reads two independent policies — is a subject *relevant* (`theme`), and may
  it be written about *at all* (`.wikicommit/entity-policy.md`) — and init asked about only the first.
  - Prose policies can be written after init, because they are re-read on every run. A switch cannot:
    it has a default, it acts without saying so, and the run it acts on is the first
    `/wikicommit-generate` — the one whose pages most later pages end up linking to.
  - **Neither direction can be undone afterwards.** Pages already written survive turning it on (the
    regeneration mode does not re-run that pass), and entities already excluded are not revisited by
    re-registering the same source (its hash still matches, so the later passes never run). So there
    is no "safe default" to pick; the answer has to be a decision.
  - **A blank Enter is still no**, which is what every repository created so far has. The default is
    unchanged and there are four reasons it stays that way, now written down where the next person to
    propose flipping it will find them.
  - The question says who is *in* as plainly as who is out — public figures acting publicly, and
    historical figures, normally belong in a wiki. One pilot that excluded people through `theme`
    alone ended up with no `Person` pages at all, including three historical figures named repeatedly
    in its own body text.
  - **A re-init never asks and never rewrites the file**, which by then holds prose you have written.
  - Non-interactive runs do not ask; they say once that the switch is off and that it is worth
    deciding before the first `/wikicommit-generate`.

- **A review that noticed something while passing a page now leaves a record of it** (Issue #834).
  Pass 4 can remark on how a page is written without that remark being a defect — an imprecise
  phrase, two distinct things collapsed into one. Those remarks reached the console and stopped
  there, so a page reviewed with a remark and a page reviewed in silence came out byte-identical
  on disk (`result: pass`, `findings: []`). That is the same shape as a page that failed once and
  was fixed looking like one that never failed, one scale smaller.
  - The review returns them in an `observations` array and they land in the review record's
    **prose body**, where a person reading `.wikicommit/review/` finds them.
  - They are deliberately **not** findings. The list a person picks pages to read from counts
    findings, and filling it with non-blocking remarks would change what that list means while
    its selection rule is still being measured.
  - Two limits keep this from becoming noise: it covers only what the page *states* (a review
    still never reports "the evidence covers more than this"), and a review with nothing to add
    writes nothing.
  - Written once in the shared rules file, so all three review paths state them. The two
    that run a subagent (`wikicommit-generate` Pass 4, `wikicommit-synthesize` Step 5.5)
    write them into the record; `/wikicommit-review` has no subagent and no separate body
    to write, so it reports them to the reviewer it is already talking to.
    `rules_version` is bumped to 3.

- **`/wikicommit-generate <url>` now stops on an `index_only` domain instead of registering it**
  (Issue #833). `index_only` in `.wikicommit/source-policy.md` names domains this wiki reads for
  their reference lists and never registers, and until now only `/wikicommit-collect` consulted
  it. Handing such a URL straight to `/wikicommit-generate` — the main path — fetched it and
  built pages from it, with nothing in the way: the domain guard in Pass 1 unions only its
  built-in list and `exclude_domains`.
  - What that setting protects is not a preference. What the wiki wants from such a domain is
    the sources it cites, not the article itself: a page built from one such article and
    nothing else tends to be a shorter retelling of it without its footnotes, and where the
    article is share-alike licensed that page carries the obligation too. Registering it does
    record and display it as a source — what is at stake is the decision, not the attribution.
  - It **asks** rather than blocks, the same shape `exclude_domains` and `rejected:` already
    have, and with the same host comparison (scheme, port, path and a leading `www.` ignored, exact
    match otherwise). Registering such a domain by name stays supported: some subjects have no
    primary source at all, and the policy deliberately stops short of banning encyclopaedias.
  - The question points at `/wikicommit-collect --index <url>`, which reads that page's
    reference section and pulls the primary sources out of it.

- **The review rules no longer give two opposite verdicts on the same sentence** (Issue #832).
  Check 1 (is the claim in the evidence?) and check 4 (is the specifically dated or titled
  document the page names actually here?) both applied to "a fact about another document that
  the source states as its own subject", and they disagreed. In a pilot one source produced
  two pages that both carried "Martin Fowler coined *semantic diffusion* in 2006": on the page
  about that term it passed, on a neighbouring page it failed twice — same evidence, same run,
  and the wiki ended up stating the fact on one page and withholding it on the other.
  - Check 4 now stops where the evidence is **about** the fact rather than mentioning it in
    passing; that case is check 1's. The subject-matter test is not new — check 7 already uses
    it between two sources, and check 4 already named one half of it ("a source's own *passing
    mention* of a different document") without naming the other.
  - The boundary is written on **both** sides. A rule stated on one side only gets applied on
    one side only.
  - Nothing check 4 was written to catch is loosened: a page citing "the March 19 post" while
    holding only a later article by the same author still fails, because that post is something
    the later article mentions rather than what it is about. Where a fact could be read either
    way, it counts as the passing mention and fails.
  - The carve-out covers the page *stating* such a fact, not citing a document for it. A title,
    URL or dated post the page names as where the fact came from still fails when it is not
    among the evidence, however squarely that evidence is about the same fact — otherwise the
    carve-out would swallow the explicit citations check 4's first sentence is about.
  - **Consequence worth knowing:** claims of this kind now pass, so they stop appearing in the
    `MISSING_SOURCE` roll-up of documents worth registering. That roll-up only sees failures.
  - `rules_version` is bumped to 2, so a review that read the old file is told apart from one
    that read this one.

- **`/wikicommit-init` now offers to run the foundational commit, instead of only printing it**
  (Issue #843). The guidance it ends with has always been the one thing in the flow handed back
  for you to run by hand, on two grounds that had both stopped holding: `.wikicommit/schema/` is
  written by `init.py` itself, and the obvious-type judgment has the agent write a schema file
  directly, so what that rule forbids is *authoring*, not recording what one just authored; and
  the invariant is not "never touch the default branch" but "an LLM's authored knowledge goes
  through a PR" — a rule this commit falls outside of, since its content is deterministic
  template expansion plus type files you approved with Enter, and since `/wikicommit-init` is
  often a repository's first commit, with no base branch and possibly no remote to open a PR
  against.
  - It shows `git status --short --untracked-files=all`, asks **once**, and defaults to no. On a
    yes it runs `git add -A`, commits with the message the guidance printed (carrying the same
    `Co-Authored-By` / `Generated-By` trailers `wikicommit-merge` writes), and pushes.
  - Every path that does not end in a commit falls back to the printed guidance unchanged, so
    nothing is weakened: a decline, a non-interactive run, or any failure (no remote, no
    upstream, branch protection, a pre-commit hook) leaves the commands on screen for you.
  - Two situations hold the offer back, and neither is about permission: WikiCommit added to
    a repository that already had its own `.gitignore` (where `git add -A` would reach past
    WikiCommit's own output), which ends it; and a "Set up Quartz v5" step still listed above the
    commit step (where committing first would split the foundational commit around
    `git submodule add`), which only postpones it — see the entry under "Fixed" below for how it
    resumes.

- **`reconcile_ingest_status.py` no longer touches a `pending` source that already lists
  `generated_pages`** (Issue #874). The script exists to repair one specific state: a source whose
  pages were written during a run while its own `status`/`generated_pages` were never written back
  — a file left at `status: pending` with `generated_pages: []`. It had no way to tell that apart
  from a source deliberately put *back* into the queue, and a requeued source matches every one of
  its tests by construction (a source that made pages has its hash cited by them), so it was
  flipped straight back to `generated` under a `RECONCILED:` success line.
  - The path that reaches this today is a source file you edited and then restored: re-registering
    it moves the management file from `outdated` to `pending` so the next `/wikicommit-generate`
    rebuilds its pages, and that request is now honoured rather than cancelled at the end of the
    run.
  - A source that produced no page at all is unaffected either way — its hash appears in no page's
    `sources[]`, so the existing match test already left it alone.
- **`/wikicommit-review` now checks for the review rules before it asks you anything** (Issue #888).
  The Skill stops when `.wikicommit/review-rules.md` is missing — reviewing without it would quietly
  degrade to "does the page match the source" while still recording that a review happened — but it
  used to reach that check only part-way through the fact-check step. By then it had already had you
  complete the page's frontmatter, register a `sources` entry, confirm a hash, and wait for every
  source document to be fetched, for a review that was never going to run. The other two review
  paths (`wikicommit-generate` Pass 4 and `wikicommit-synthesize` Step 5.5) already checked at the
  start of the run; this one now does too.

- **`/wikicommit-status` now says what the review sampling list actually selects on** (Issue #765).
  `RISKY:` is described as "two attempts, or at least one finding", and measuring a pilot's 28 pages
  showed the two are not independent: a finding fails the review, which makes it retry, so no record
  held a finding at one attempt and the twelve pages listed were exactly the twelve with two
  attempts. The wording says so now. **The rule itself is unchanged** — the finding side still counts
  on its own for a non-blocking `page_at_fault: "other"`, and for a human review, which never
  retries.

### Fixed

- **`--include-source` no longer feeds a withdrawn source into an answer** (Issue #918).
  `status: retracted` records that a person read a document and judged its content unreliable
  (Issue #737) — the one judgment a machine cannot reach on its own, because the evidence-bound
  rule makes a source the yardstick rather than the thing being judged. The ingest side stops
  re-registering such a source and stops it returning to `outdated`; the reference side had no
  guard at all, so `/wikicommit-ask --include-source` read its cached text and injected it as
  answer grounding.
  - `resolve_source_cache_path.py` now answers a retracted source with a `RETRACTED:` line
    naming the management file, and **exit code 2**. Exit 1 could not carry it: it already
    folds two meanings together, and on the `type: path` route the caller answers exit 1 by
    reading the raw file — so a retracted source that was never cached would have gone straight
    through the fallback.
  - The status is read **before** the cache is looked up, for the same reason. Checking after
    would guard exactly the sources that happen to be cached and miss the rest.
  - The path the script prints is where the `## Retraction Reason` lives. No enum carries the
    reason — a person wrote it in that file, and that is the only place it exists.
  - **Only `retracted` is read.** `failed`, `excluded`, `partial` and `outdated` describe how
    ingestion went, not what anyone thinks of the document; reading them would put a second
    interpreter of the whole `status` vocabulary on the reference side.
  - `type: manual` sources stay out of scope: they have no management file, so there is no
    `status` to read.
  - A management file whose frontmatter will not parse is skipped with a `WARNING:` on stderr
    rather than in silence. `status: retracted` is hand-written and nothing validates a source
    management file, so a typo made while writing the retraction would otherwise leave the
    source looking unregistered — the ordinary miss, which the `type: path` route answers by
    reading the raw file.

- **Two more routes read a withdrawn source; both now drop it before fetching** (Issue #928).
  Issue #918 closed `/wikicommit-ask --include-source`, but `wikicommit-review` and `wikicommit-fix`
  also re-fetch a page's `sources[]`, and they go straight to the file or the URL rather than
  through `resolve_source_cache_path.py` — so that guard could not reach them by construction.
  - **The review route was the sharp one.** Checking a page against a document a person has judged
    unreliable passes the page *because* it is faithful to it. The contradiction was closed inside a
    single file: the same instructions tell a reviewer who finds a source wrong to write
    `status: retracted` by hand, and the next run then ignored what they had written.
  - **Neither route stops.** The withdrawn sources are dropped from the evidence and the check runs
    on what is left, which is what buys information nobody had: the sentences that stood *only* on a
    withdrawn document surface one at a time. `check_retracted_sources.py` can name the page but not
    the sentence, and the sentence is what decides between `--regenerate`, `/wikicommit-fix` and
    `/wikicommit-remove`. The finding is worded as "this stood only on a withdrawn source" rather
    than "this page is wrong" — the latter pushes a reviewer to cut text when regenerating is the
    right move.
  - Blocking was considered and rejected: a page would then be unable to reach `reviewed` until
    someone acted, which adds a third state to the trust ladder through the back door. What
    `reviewed` claims is that a person read it and nothing jumped out, not that its sources are
    sound, so a signature given in full knowledge of the withdrawal is not a false one.
  - `check_retracted_sources.py` gains `--list`, which walks the source tree only and prints the
    same `RETRACTED:` line the resolver prints. No new script was added: the identity rule
    (`source.path` / `source.url`, never the derived filename) stays in one place.
  - **`/wikicommit-fix` had no entrance either.** A comment saying "this source is wrong" ended with
    the Skill declining to make an unsupported edit — correct as far as it went, but the answer is
    that this is a withdrawal rather than an edit, and it now says so.
  - The judgment happens **before** the fetch, and after `sources` has been resolved: fetching first
    costs a round trip and puts the withdrawn text into context, where "do not use it" becomes a
    matter of instruction-following; resolving first is what makes a translation page — which
    inherits its sources from its parent — take the guard at all. The `derived_from` route is
    deliberately left out, as the pages it reads carry no `status`.
  - If `--list` is unavailable the routes warn and carry on. That is the behaviour from before this
    version, and in a wiki with no withdrawn sources it changes nothing either way.

- **The foundational-commit offer was unreachable for every Quartz user** (Issue #865).
  `/wikicommit-init` offers to run the commit it just generated the files for, and withholds that
  offer while the printed guidance still has a "Set up Quartz v5" step above the commit step —
  committing ahead of `git submodule add` would split the commit in two. But that condition holds on
  **every** first `--quartz`/`--quartz-pages` run: the setup check can only report Quartz as set up
  once `quartz/` exists, which on a first run it does not. Re-running `/wikicommit-init` afterwards
  did not reach the offer either, because a second run skips the `.gitignore` it already wrote and a
  different condition fires on that. So the motivating case for the offer was still being done by
  hand.
  - That condition is now a **deferral** rather than a skip. `/wikicommit-init` asks you to run the
    printed Quartz commands and to say when they are done, re-checks the setup status, reprints the
    guidance — where the commit step is now first — and makes the offer against the reprint. Declining
    or saying "later" leaves the printed guidance as the answer, exactly as before.
  - **`git submodule add` still stays with you.** The agent asks for it rather than running it: a
    submodule changes the repository's structure and fails in its own way, which is out of scope for
    this offer rather than settled by it.
  - Nothing new to invoke, and no new flag. The agent already holds every other value it needs from
    minutes earlier, so only the Quartz status is re-derived.

- **The foundational-commit offer stayed withheld on every later `/wikicommit-init`** (Issue #873).
  The offer is withheld when `git add -A` would sweep up files that are not WikiCommit's, and that
  was decided by asking "did this run write `.gitignore`". A repository created by WikiCommit
  answers no on every run after the first — the file is already there and is never overwritten — so
  the case the offer exists for was the case that never received it. A first `--quartz` run could
  print both `SKIPPED: .gitignore` and `UPDATED: .gitignore` for the same file, and the condition
  read only the first of them.
  - The question is now whether **this repository's `.gitignore` holds the template's patterns**,
    which is what the old condition was standing in for. `init.py` prints one line
    (`GITIGNORE_READY: yes` / `no (missing: …)`) and the Skill reads that line rather than the file.
  - Exposure does not widen. `.wikicommit/.cache/` and `.wikicommit/run/` are WikiCommit's own
    paths, so an unrelated repository does not list them by accident; one that does listed them
    because this guidance asked for it.
  - A repository predating a pattern the template gained later — `.wikicommit/run/` arrived with the
    run records — answers `no`, and that is the correct answer rather than a false one: `git add -A`
    there really would stage run records, and `check_distribution_freshness.py` reports the same gap.
  - The same function backs the selective-`git add` note that gets printed, so the offer and the note
    can no longer disagree about one repository.

- **A run that stamped no pass at all was the one case `Runs that skipped a pass` never
  reported** (Issue #864). `check_run_records.py` gated `MISSING_PASS:` on the record
  carrying at least one stamp, which correctly excluded records written before stamping
  existed — and incorrectly excluded records written after it that stamped nothing.
  Context compaction does not drop a predictable share of the stamping instructions: when it
  drops all of them the record holds an empty list, and `missing_pass=0` was printed. The
  line fired on partial loss and fell silent on total loss, which is the wrong way round.
  - The gate now asks whether the record carries the `passes` key at all. `record_run.py`'s
    `start` writes it empty on purpose, so "stamped nothing" and "could not have stamped"
    were already distinguishable on disk; only the reader was not using the distinction.
  - Such a run is reported **only when the record shows it did work** — a source or page it
    named, or an outcome count that is not zero. Finishing with no stamp is legitimate and
    usual otherwise: a bare `/wikicommit-generate` on an up-to-date wiki finds no management
    file to process and exits, and reporting that would put this line on most runs, which is
    how a line stops being read. A run that halted before the first pass records no work
    either, so it falls out through the same gate without a rule of its own.
  - The line reads differently for this case — it says the run stamped no pass at all and
    names the work the record holds, rather than listing five passes as though each had been
    skipped separately. That is the stronger finding, not a milder one.
  - Skills with no declared passes cannot produce a false positive here: the report still
    requires a missing expected pass, and only `wikicommit-generate` declares any.
  - `/wikicommit-generate`'s "No management files to process" exit now closes the run record
    explicitly. That exit is the one taken most readily, usually before the rest of that file has
    been read, and the general rule about closing the record sat at the top — so a run that
    finished correctly could be reported as one that did not finish, on every `/wikicommit-status`
    from then on. Closing it with nothing named is also what distinguishes a no-op run from one
    that lost its stamps.
  - The evidence clause names every shape the work gate accepts, including the loose ones a
    hand-edited record can hold (a bare scalar where a list belongs, a non-mapping
    `outcome`). Counting only well-formed lists and mappings printed this line — the
    strongest finding it produces — with no stated basis at all, while the summary is the
    only place that basis appears.
  - `Runs that skipped a pass` still says out loud that a 0 is not proof no pass was
    skipped: the closing call is what records the work, so a run that lost its stamping
    instructions and also closed without naming a source, page or outcome reads as a run
    that had nothing to do.

- **A run that halted was counted as one that finished** (Issue #872). Both halt paths — the
  missing extraction package, and a review-rules version mismatch — close the record through
  `record_run.py end --halted-reason`, so it carries an `ended_at`; and `ended_at` was what "did it
  finish" was read from. The result split two ways: a halt still missing some stamps was printed
  under `Runs that skipped a pass` with the word *finished* in it, and a halt with every stamp in
  place produced no line at all.
  - The second case was structural rather than a near miss. Expected passes are defined for
    `wikicommit-generate` alone, so a halt in `wikicommit-synthesize`, `wikicommit-translate` or
    `wikicommit-merge` has an empty expectation and therefore no missing stamps — no amount of
    fixing that line would have reached it.
  - One predicate — closed, and not halted — now feeds both lines, so a halt falls out of the
    skipped-pass line without a branch of its own. The reason and the elapsed time are printed with
    it: a halt before the first fetch and a halt after the review passes are minutes apart, which is
    why the record still closes rather than leaving `ended_at` empty.
  - No new prefix and no new summary key, so nothing that reads this output had to change. The cost
    is that "forgot to stamp the end" and "halted" are told apart by `halted_reason` alone — but
    that was already the only value separating them, and it is printed on the line.

- **`Wiki is healthy` could not be reached, no matter how sound the wiki was** (Issue #836).
  `/wikicommit-status` withheld that verdict until every category read 0, and two of the
  categories in that list are not defect counts at all.
  - `Unreviewed pages` — renamed to **`Pages not yet read by a person`**, and no longer part
    of the verdict. Since Issue #800, `reviewed` means a person read the page, and the same
    decision settled that the machine review covers every page while the human one is a
    sample. Requiring 0 there was requiring 100% human review, which is the opposite of what
    was decided. A pilot wiki with all 28 pages checked against their sources, and every
    other category clean, still could not be called healthy.
  - `Wanted pages` — likewise no longer part of the verdict. A wanted link is a page the wiki
    has said it would like to have; Issue #340 stopped blocking on them because blocking
    teaches writers to drop the WikiLink rather than write the page, and demanding 0 restores
    that same pressure aimed the other way — at writing a page the sources do not support.
  - `Type-mismatched links`, which prints right beside it, **still gates**, and the reason is
    now written down: there the page already exists under a different Type, the mistake is one
    word in one link, and it can and should be 0.
  - The two similarly named rows — `Pages not yet read by a person` and `Pages with no
    standing review` — are far apart in the output and a pilot read them as one number. Both
    now say in their own line which question they answer, and the output rules say to tell them
    apart whenever both are printed — not only when they disagree, since the pilot's own reading
    was 28 against 0.

- **The printed first-commit guidance could not be run as printed** (Issue #842).
  `/wikicommit-init` ended by listing every path to `git add` — 25 of them with
  `--quartz-pages` — and two of those, `.gitmodules` and `quartz`, are not generated by
  anything: the user creates them with `git submodule add` in an earlier step. `git add`
  aborts the whole command on a pathspec that does not exist and stages nothing, so anyone
  who copied the commands in order, or came back to Quartz later, got no foundational commit
  at all — the state that step was added to prevent.
  - The default is now `git add -A`. `.gitignore` is written by the same run, so in a
    repository made for the wiki this stages exactly WikiCommit's own output. The per-path
    list is still printed underneath, for the one case where it is the right tool: WikiCommit
    added to a repository that already has files of its own, where `-A` would sweep those
    into the same commit.
  - That second case gets the two caveats it needs, because neither is obvious from `-A`
    itself. An existing `.gitignore` is never overwritten — only a Quartz section is appended
    — so a repository whose own ignore file does not already list `node_modules/`,
    `.wikicommit/.cache/` and `.wikicommit/run/` would commit them; and the per-path list
    printed for that case still names `.gitmodules` and `quartz`, so it still aborts whole if
    `git submodule add` has not run yet.
  - A dirty Quartz submodule working tree is not swept in either: `git add -A` at the
    repository root stages the submodule only when its commit pointer actually moved, which
    for the first commit is what you want.

- **`/wikicommit-status` never reported a run that skipped a pass** (Issue #835).
  `check_run_records.py` emits three kinds of line, but `MISSING_PASS:` appeared nowhere in
  the Skill that reads it, so the result was computed and thrown away on every run. The row
  `Runs that skipped a pass` now appears alongside `Last run` and `Runs that did not finish`.
  - What went unreported is the half of the per-pass stamps that answers *whether a run
    skipped a step and carried on* — the failure this project has hit three times, each time
    found by a person auditing a published wiki by hand. Like the other two run rows it does
    not gate the "healthy" verdict, and it is a prompt to look rather than a defect: a run
    whose sources were all blocked or all already current has nothing for the later passes to
    do.
  - `check_run_records.py` is unchanged; only the reading side was missing.

- **Entities excluded from page generation were named, with the reason, on the public
  source page** (Issue #831). `exclude_note` and `coverage_gap_note` were appended to the
  source management file's `## Summary`, on the premise that management files are internal.
  Issue #476 ended that premise by mirroring every management file to a public page under
  `content/sources/`, and `## Summary` is one of the sections it renders — so the result of
  applying `exclude_living_persons`, a switch whose whole point is not to write about a
  person, was published under that person's name, together with the internal identifiers
  behind the decision (`.wikicommit/entity-policy.md`, the setting key, the type file whose
  `properties:` block lacked a field).
  - Both notes now go to a separate `## Generation Notes` section. `## Summary` holds only a
    summary of what the source says. Nothing else changed: the public page still renders the
    summary, and the new section is private because `_write_source_page()` renders a
    whitelist of sections — the same reason `## User Notes` and `## Failure Reason` have
    always been private.
  - **Existing management files are not migrated, and a plain run does not clear them.**
    Summary and notes were never delimited inside `## Summary`, so they cannot be separated
    mechanically. Nor will the next `/wikicommit-generate` rewrite them on its own: a source
    whose entities were all excluded ends at `status: excluded`, and one where only some were
    ends at `status: partial` with an empty `failed_pages`, and a run with no argument
    collects neither — which is exactly the two states whose `## Summary` holds the notes.
    So fix such a file deliberately: edit its `## Summary` by hand and run
    `/wikicommit-merge`, or re-run that source by name
    (`/wikicommit-generate <path|url>`), which is processed whatever its status.

- **`review-issue-close-sync.yml` never started, so closing a review tracking Issue did
  nothing** (Issue #830). The copy shipped in 0.5.0 spelled an empty `${{ }}` out literally
  inside a `run:` body, in a comment explaining that a value is *not* interpolated. GitHub
  expands expressions in a `run:` body before the shell ever sees it — a shell comment is
  still expanded — so an empty one is a parse error that takes the whole file down. The
  workflow went to `startup_failure` with zero jobs, which leaves no log and shows the file
  path instead of the workflow's `name:` in the Actions list.
  - On a wiki this meant that closing a tracking Issue no longer wrote
    `review_status: reviewed`, no longer recorded the human review, and no longer opened the
    follow-up PR. Pages stayed `pending` with no error surfacing anywhere, and
    `/wikicommit-status` went on counting them as never read.
  - **If you installed 0.5.0, re-sync to pick the fix up.** This workflow is
    `update: overwrite` (Issue #712), so `/wikicommit-update` — or
    `/wikicommit-init --no-overwrite` — replaces it. Tracking Issues you closed while it was
    broken were never acted on; reopen and close one again and the sync runs, as the
    workflow triggers only on `issues: closed` and is a no-op on a page already `reviewed`.
  - `tests/test_workflow_template_expressions.py` now fails on an empty (or unclosed)
    expression anywhere in a distributed workflow template or in this repository's own
    workflows.

- **`/wikicommit-schema-propose` named the wrong thing for its post-review flow** (Issue #938). It
  pointed at something that opens no pull request at all; what opens one after a review and merges
  it on a passing quality check is `review-issue-close-sync.yml`. The reference now names that.

### Notes

- **No type template (`.wikicommit/schema/`) changed in this version** — every one is
  byte-identical to 0.5.0. `wikicommit-generate`'s instructions were split across files under
  `references/`, but that is where the text lives rather than what it says, and the rules that did
  change (Issues #832, #834, #910) govern how a review is judged and what a run does when it
  cannot decide, not how a page gets written. **There is therefore no reason to regenerate pages
  for this version.**
- **A new Skill does not arrive through `/wikicommit-update`.** `/wikicommit-reconcile`
  (Issue #874) is a Skill rather than part of the template tree, so install it first —
  `npx skills add wikicommit/wikicommit --skill '*' --agent claude-code -y --copy`, or
  `install.sh` — which is what `/wikicommit-update` itself asks you to do before it runs.
- **What reaches an existing wiki repository through `/wikicommit-update`**: the new
  `.wikicommit/guides/` shelf (Issues #846, #867), `.wikicommit/schema-authoring.md`
  (Issue #886), the review rules at `rules_version: 3` (Issues #832, #834), the new
  `check_schema_files.py` and `read_policy.py`, and the graph plugin (Issues #838–#841). All of
  them are `update: overwrite`. The graph changes are reader-facing, so they need one `deploy.yml`
  run after that.
- **What does not arrive on its own**: `.wikicommit/entity-policy.md`, which is `update: review`.
  `/wikicommit-init` now asks about `exclude_living_persons` (Issue #837), but an existing
  repository keeps the file it has, with the value it has — the question is asked at
  initialisation, and nothing rewrites your policy file behind you.
- **Reviews recorded before this version carry `rules_version: 1` or `2`.** A record says which
  version of the rules judged it (Issue #834); an older number is an earlier review rather than a
  worse one.
- Nothing is applied retroactively. A changed policy does not revisit pages already written:
  `/wikicommit-reconcile` puts the *sources* back in the queue and the next `/wikicommit-generate`
  rewrites what it can, but a page whose entity is now excluded stays where it is until
  `/wikicommit-remove` takes it down — the guide added in this version (Issue #867) walks through
  what is left to do by hand.
