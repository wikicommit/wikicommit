## 6. パイプライン実装

### 6.1 Ingest（`/wikicommit-generate`）

ソースの登録と Wiki ページ生成を一括で行う。Git 操作は行わない。

> **ingest 対象の実ソースファイル（`raw/` 等）のコミットタイミング**（Issue #106）: `wikicommit-generate` 自体は Git 操作を行わないため、リポジトリに新規追加した生ソースファイル（例: `raw/paper-2024.pdf`）は untracked のまま残る。このファイルは `wikicommit-generate` ではなく `wikicommit-merge`（§6.2 ステップ 2 の 3.）が、bulk update PR を作成するコミットに未追跡分のみを含める形でコミットする。既にリポジトリに存在していた既存ファイル（例: `src/auth.py`）を ingest 登録した場合はこの対象外（追跡済みのため何もしない）。

#### 対応ソース種別

| ソース | コマンド例 | 管理ファイル生成先 |
|---|---|---|
| リポジトリ内ファイル | `/wikicommit-generate raw/paper-2024.pdf` | `.wikicommit/source/path/raw/paper-2024.pdf.md`（元の拡張子を保持。Issue #573。既に同じ `source.path` を持つ管理ファイルがあればその実パスを使う） |
| リポジトリ内ファイル | `/wikicommit-generate src/auth.py` | `.wikicommit/source/path/src/auth.py.md` |
| リポジトリ内ディレクトリ | `/wikicommit-generate src/ --include "**/*.py"` | `.wikicommit/source/path/src/` 配下にファイルごとに生成 |
| 外部 URL | `/wikicommit-generate https://example.com/article` | `.wikicommit/source/url/example.com/article.md`（ホスト名ディレクトリ + パス+クエリのファイル名。Issue #191・#572。既に同じ `source.url` を持つ管理ファイルがあればその実パスを使う。詳細は [DesignDoc-data.md §4.3](DesignDoc-data.md) 参照） |

#### 処理フロー

```
引数を解析してソース種別を判定
  ├─ ファイルパス → type: path
  ├─ ディレクトリパス → 配下ファイルを走査して type: path を複数生成
  └─ https:// URL → type: url
  ↓
対応する .wikicommit/source/ パスに管理ファイルが存在するか確認
  ├─ 存在しない → ハッシュを計算して新規作成（status: pending）
  └─ 存在する
      ├─ ハッシュ一致かつ status が outdated → status を generated にリセット（ソースが元に戻った）
      ├─ ハッシュ一致 → スキップ（変更なし）
      └─ ハッシュ不一致 → hash を更新・status を pending に変更
  ↓
処理対象の管理ファイルに対してページ生成を実行（§11.6 多段生成アルゴリズム）
  ※ 対象は status が pending / outdated、および partial かつ failed_pages が非空のもの（Issue #567。下記 callout 参照）
  ↓（管理ファイルごとに順次処理）
source.type に基づいてソースを取得
  ├─ type: path → ファイル直接読み込み
  ├─ type: url → 既知JS-shellドメインチェック（ガードB）→ 取得能力チェック（ガードC。下記 callout 参照）→ OK なら独自UA付きでmarkitdown（下記 callout 参照）
  └─ type: wikicommit → 同上（独自UA付きmarkitdown・フェデレーション取得）
  ↓ 抽出 Skill でテキスト変換
  ↓ 失敗（空・読み取り不能・既知JS-shellドメインでブロック） → そのソースをスキップ（エラーをコンソールに出力）
  ↓ 低情報密度チェック（ガードA。下記 callout 参照）→ 低密度なら人間に続行可否を確認（非対話実行時はそのソースをスキップ）
LLM への入力:
  - 抽出テキスト
  - .wikicommit/schema/ 型候補リスト
  - 管理ファイル body の ## User Notes（あれば）
  - .wikicommit/entity/ の既存ページ一覧
  - .wikicommit/config.yml の theme（空なら関連性の判定なし）
  - .wikicommit/entity-policy.md（exclude_living_persons と散文本文。
    無い・off・散文が空なら許容性の判定なし。Issue #667）
  ↓
LLM が分析 JSON を生成（§11.6 パス 2）。エンティティごとに action を判定:
  ├─ create      → 新規ページを作成
  ├─ update      → 既存ページに新情報を統合
  ├─ ambiguous   → スキップしコンソールに記録（型を人間が確定するまで保留）
  └─ exclude     → ページ化しないと判断。exclude_reason / exclude_note を記録（人間確認なしで自動スキップ）
      ※ theme_mismatch（関連性）と privacy（許容性）の2軸を独立に判定する
      ※ theme が空なら theme_mismatch の判定のみ行わない。entity-policy.md が
        空・未設定なら privacy の判定のみ行わない（両方なら従来通り全生成）
  ↓
分析 JSON の summary を管理ファイル body の ## Summary に書き込む（exclude したエンティティがあれば理由も含める）
  ↓（create / update のエンティティのみ）
[レビューサブエージェント] 各ページをソース元文書と照合
  ├─ PASS → ローカルに書き出し
  └─ FAIL → 再生成（最大 generate.max_retries 回）
              上限超過 → そのページをスキップ。エラーをコンソールに出力
  ↓（次の管理ファイルへ）
全管理ファイルの処理完了後:
影響を受けた Type ディレクトリの index.md をローカルで更新
  ↓
各管理ファイルの status をローカルで即時更新:
  ├─ 全エンティティ成功（exclude なし）        → status: generated、generated_pages を記録
  ├─ 一部失敗 or 一部 exclude（1件以上は成功）  → status: partial、generated_pages と failed_pages を記録
  ├─ 全エンティティが exclude（成功 0 件）      → status: excluded
  └─ 全エンティティが生成失敗                  → status: failed
```

#### 再生成モード（`--regenerate`。Issue #578）

既に生成済みの Wiki ページを、現在のスキーマテンプレート・生成ルールで作り直すモード。上記の通常フローがソース起点（ソース管理ファイルの `status` が `pending`/`outdated`、および `partial` かつ `failed_pages` が非空のものだけを処理し、`generated` は `SKIP` する）である以上、「ソースは変わっていないが生成ルールが変わったので作り直したい」という要求は通常フローでは表現できない。

```
/wikicommit-generate --regenerate <page-path>     # 単一ページ
/wikicommit-generate --regenerate --type <Type>   # 型単位（全言語）
/wikicommit-generate --regenerate --all           # 全対象ページ（5件超なら確認）
```

```
対象ページを選別（下記「対象外」に該当するものを除外し、除外理由を都度報告）
  ↓ 5件超過 → 全件処理 / 先頭5件のみ をユーザーに確認（generate/collect/translate と同じ閾値）
ページの sources: を再取得（Pass 1 の抽出ルールをそのまま使う）
  ├─ status: retracted のソース → 取得しない。落として残りで作り直し、
  │                                ページの sources: からもそのエントリを外す（Issue #744）
  ├─ type: url/wikicommit → キャッシュ（.wikicommit/.cache/ingest-fetch/）の SHA-256 が
  │                          ページ記録の hash と一致すれば再フェッチしない
  │                          （管理ファイルは source.url の実走査で特定する。
  │                            add_source.py --check-hash は管理ファイル側の
  │                            現在の hash と比較するため、この用途には使わない）
  └─ 再取得結果の hash がページ記録の hash と食い違う
        → そのページは再生成しない。既存の outdated フロー（/wikicommit-generate <path|url>）へ誘導
  ↓
Pass 3（生成）— action: update・existing_path = そのページ自身として実行
  ↓
Pass 4（レビュー）— 変更なし。max_retries 超過なら既存ページをそのまま残す
  ↓
rebuild_index.py（title が変わりうるため）
```

**Pass 2・Pass 2b は実行しない**。対象ページの frontmatter が `type`/`title`/slug/`lang` をすべて持っており、抽出すべきエンティティが既に確定しているため（ソース起点ではなくページ起点にした理由でもある — 1 つのソースが複数の型のページを生成している場合、ソース起点の再処理は無関係な型のページまで巻き込む。ページは `sources:` に自身の出自を全件持っているため、複数ソースからマージされたページも含めてページ単位で作り直せる）。

**再生成後は `review_status: pending` に戻す**。Pass 3 の `action: update` はかつて既存の `reviewed` を無条件に維持しており、当初この節はそれを「増分マージ向けのルールであり、人間の以前のレビューがページの大半を依然カバーしている」として正当化していた。**Issue #724 がその正当化を否定した** — 同じ分岐が本文・`properties`（`description` を含む）・`tags`・`expires_at` を新しいソースの情報で書き換える以上、「大半がカバーされている」は成り立たない。現在は `action: update` も、内容が実際に変わっていれば `pending` に戻る（`reset_review_on_content_change.py`。§6.3 参照）。したがって再生成が `pending` に戻すのは `action: update` に対する**例外ではなく、同じ原則の適用**である — ページの構造そのものを作り直す再生成では、人間が一度も読んでいない内容に「レビュー済み」の証明が引き継がれてしまう（信頼ラダーの意味が壊れる）。`pending` に戻ったページは次の `/wikicommit-merge` の全ページ走査が拾ってレビュー追跡 Issue を新規作成する — 過去に同じページの Issue が Close 済みでも、スキップ判定は **open な** Issue のみを見るため正しく立つ（既存の仕組みへの変更は不要）。あわせて `reviewed_by`（Issue #663）も出力に含めない — 前の版に署名した人の名前であり、`pending` の隣に残すと次に `reviewed` へ到達したときに再浮上する（Issue #705。Pass 3 はページ全体を書き直すため、出力に含めなければそれで消え、削除の手順は要らない）。安全弁として、再生成結果が既存ページと**書き換え対象の5フィールド（`review_status`/`reviewed_by`/`generated_at`/`generated_by`/`generated_with`）を除いてバイト一致**する場合のみ `review_status` を維持し、そのとき `reviewed_by` も維持する（名前だけを落とすと、弁が守ろうとしている「実際に人間がレビューした版のままである」という事実を片側だけ壊す）。`reviewed_by` は書き換えではなく削除の対象だが、それでも比較の除外に含める必要がある — 含めないと、rebuilt 側にその行が無いこと自体が差分として数えられ、`reviewed_by` を持つページ（＝経路 A を通った全ページ＝この弁が守る対象そのもの）では弁が決して発火しなくなる。判定を意味的同一性ではなくテキスト一致にしたのは、非決定的な判定に「人間のレビューが要るか否か」を委ねないため（LLM 出力は決定論的でないため、この弁が発火することは稀と見込む）。

**対象外**（該当ページはスキップし、理由を都度報告する）:

| 対象外 | 理由 |
|---|---|
| `index.md`・`status: removed` のページ | 生成物ではない / 公開対象外 |
| `translated_from` を持つページ（翻訳） | `/wikicommit-translate` の所管。原文ページを再生成すれば `check_translation_status.py` が `STALE` として検出するので、追随の新機構は作らない |
| `derived_from` を持つページ（合成） | 同上（`/wikicommit-synthesize`・`check_derivation_freshness.py`） |
| `sources` が無い / `sources[].type: manual` を 1 件でも含むページ | 再取得できるソースが存在しない。残りのソースだけで作り直すと manual 由来の記述が黙って消えるため、ページ単位でスキップする方を採る |
| `sources` の**全件**が `status: retracted` のページ（Issue #744） | 取り下げ済みソースは取得せず落とすため、作り直す材料が 1 件も残らない。`/wikicommit-remove` へ誘導する（根拠が 1 つも無いページは削除の判断であって再生成の判断ではない）。**1 件でも残るページはスキップしない** — 取り下げたエントリを落として残りで作り直すことが、まさにこのモードの役目である |

**ソース管理ファイルへの書き戻しは一切行わない**。再生成は新規ページを作らないため `generated_pages` は変わらず、`last_generated_at`（ソースをページ化した日）はこの操作が記録すべき値ではない。管理ファイルに触れないことで `check_ingest_freshness.py` が `source.hash` を参照点として保持する設計とも干渉しない。したがって Pass 1・Pass 4 は**取得と生成の部分だけを流用し、管理ファイルを書く手順は実行しない** — 具体的には Pass 1 の `--write-hash`（`source.hash` を新しい取得結果で上書きしてしまうと、`status` は `generated` のまま hash だけが進み、次に `/wikicommit-generate <url>` を実行しても `HASH_MATCH` で「変更なし」と報告され、折り込みを拒否したはずのソース変更が恒久的に見えなくなる）・`extracted_tokens`・`status: failed`／`## Failure Reason` の書き込みと、Pass 4 手順5（`failed_pages`）・手順7（`status` 更新）がこれに当たる。ガードに引っかかったソース・再取得できないソース（`type: path` の実ファイルが消えている、フェッチがエラーになる等）は、管理ファイルを `failed` にするのではなく**そのページごとスキップして報告する**（残りのソースだけで作り直すと、取得できなかったソース由来の記述が黙って消えるため — `manual` を含むページを除外するのと同じ理由）。**`status: retracted` のソースだけはこの扱いの対象外**であり、スキップではなく落として作り直す（下記コールアウト）。

> **取り下げたソースは落として作り直す — `sources[]` からもエントリを外す（Issue #744）**: `--regenerate` はページの `sources:` を**全件**再取得する設計（Issue #578）だったため、Issue #737 が `status: retracted` を導入した時点で、**取り下げの意味が再生成の経路でだけ通らない**状態が生まれた。しかも `--regenerate` は「取り下げたソースを外して残りで作り直す」という、この機能が最も役に立つ場面そのものに使えなかった — Issue #737 が「ページには触れず報告に留める」と決め、ページ側の対処を既存 3 経路（`/wikicommit-remove`・`--regenerate`・`/wikicommit-fix`）に委ねた、そのうちの 1 本が実際には機能しない。
>
> **扱いは上の「変更された・再取得できない」ソースと正反対である**。あちらがページごとスキップするのは、そのソースの内容が**まだ必要なのに手に入らない**ためで、残りだけで作り直すとそこから引いた記述が黙って消える。取り下げはその逆を言っている — その内容は**要らない**と判断されたのであり、それに立っていた記述が消えることこそが目的である。したがって:
>
> | 状況 | 挙動 |
> |---|---|
> | `retracted` を含み、残りのソースが 1 件以上 | `retracted` を落として再生成し、落としたことを（`## Retraction Reason` とともに）報告する |
> | `sources` の全件が `retracted` | スキップして報告する（作り直す材料が無い。`/wikicommit-remove` へ誘導） |
>
> 判定はページの `sources[]` からソース管理ファイルを引いて `status` を読む — `add_source.py` の `find_mgmt_file_for_url()` / `find_mgmt_file_for_path()` と同じ実走査による同一性判定（Issue #572 / #573）に乗るため、旧命名規則の管理ファイルも取りこぼさない。
>
> **検討事項 1（`sources[]` からエントリを落とすか）— 落とす**。`sources[]` は**そのページの現在の本文が何に立っているか**という主張であり、内容を使わずに作り直したのにエントリだけ残すと、(1) ページが実際には使っていない裏付けを主張し、(2) Pass 4 が以後もその文書に対してページを照合し続け、(3) `check_retracted_sources.py` が毎回同じページを報告するのに人間には打つ手が無い、という 3 つが同時に成立する。「かつてこのソースに依拠していた」という記録がページから消えるのは事実だが、**リポジトリからは消えない** — 管理ファイルは `generated_pages[]` にそのページを名指ししたまま残り、`## Retraction Reason` も公開の `content/sources/` ページも残る。そして操作そのものは `git log` に 1 コミットとして残る（CLAUDE.md の GitOps テーゼ「監査は `git log` で完結する」）。
>
> **検討事項 2（`review_status`）— 追加の判断は要らなかった**。エントリを落とせば unchanged-output valve の比較対象（`review_status`/`reviewed_by`/`generated_at`/`generated_by`/`generated_with` の 5 フィールドを除く全体）に必ず差が出るため、この弁は**構造的に発火しえず**、ページは常に `pending` に戻る。これは正しい帰結である — ページが何に立っているかが変わったのであり、その状態のページを人間は一度も読んでいない。
>
> **検討事項 3（`--regenerate --retracted` のような選択子）— 追加しない**。既存の 3 指定（ページパス / `--type` / `--all`）で足りる。**対象ページの一覧は既に別の場所で決定論的に計算されている** — `check_retracted_sources.py`（Issue #737）が `wikicommit-status` Step 12 で列挙するので、人間はその出力からページパスを渡せばよい。同じ集合を求める 4 つ目の選択子は、既にある一覧の二重実装になる。
>
> **既存の公開済みリポジトリへの遡及適用は行わない**（本ドキュメント群が一貫して採る「新旧混在を許容する」方針）。既に取り下げ済みソースに立っているページは、人間が `--regenerate` を実行するまでそのまま残る。

**「どのページが古いか」の機械的検出は行わない**。鮮度検出ファミリー（`check_ingest_freshness.py` 等）への追加スクリプトは新設せず、対象はページ frontmatter の `generated_with`（Issue #577）を `grep` した結果と `CHANGELOG.md`（同）の記述を見て人間が決める。版の粒度は型より粗く、`Person.md` だけを変更して版を上げても `generated_with` 上は全ページが等しく古く見えるため、この 2 つはセットで初めて機能する。

**`granularity` 変更に伴うページの分割・統合、および既存ページの型再分類は対象外**。前者は「どのページが存在すべきか」自体が変わる操作でありページ起点の再生成では表現できない。後者は「型自体が誤っている」ページが対象で、再生成（「型は正しいが中身が古い」ページが対象）とは問題が異なる（[DesignDoc-phases.md](DesignDoc-phases.md) に着手フェーズ未確定として既記録）。

> **Wikimedia系ドメインでの403エラー対策（Issue #527）**: 当初の設計は `markitdown <source.url>` のように URL を直接渡していたが、`markitdown` 内部の HTTP クライアント（Python `requests`）が送る既定 User-Agent を Wikipedia・Wikisource 等の Wikimedia 系ドメインが `403 Forbidden` で拒否することが実地検証で判明した（[Wikimedia User-Agent policy](https://meta.wikimedia.org/wiki/User-Agent_policy) に基づく方針とみられる）。対応として、`markitdown` CLIをURL直接指定で呼ぶ代わりに、`.claude/skills/wikicommit-generate/scripts/add_source.py --fetch-url` が `markitdown` のPython API（`MarkItDown(requests_session=...)`）にWikiCommit独自のUser-Agentを設定した`requests.Session`を渡す方式に変更した。`curl`等でいったんローカルファイルに落としてから変換する方式も検討したが、その場合`markitdown`が本来HTTPレスポンスヘッダ（Content-Typeのmimetype・charset）から得ている変換方式・文字コードの判定材料が失われ、文字コードをHTTPヘッダのみで宣言している一部サイト（メタタグを持たない非UTF-8な旧式サイト等）で文字化けを起こすことを実装時に実地確認したため不採用とした。Python API経由の方式であればUser-Agentのみが変わり、HTTPレスポンスに基づく変換方式・文字コードの自動判定は`markitdown`に直接URLを渡していた場合と全く同じに保たれる。詳細な手順は `.claude/skills/wikicommit-generate/SKILL.md` Pass 1 参照。
>
> **URL ソースの鮮度検出**（Issue #310 で実装と整合するよう記述を更新）: `check_ingest_freshness.py` は `type: path` のみを定期監視し、`type: url` の自動検出は行わない。URL の鮮度確認は `/wikicommit-generate <url>` を再実行して行う — 既に `status: generated` / `failed` / `excluded`（前回の処理が完結済み）の URL ソースを再登録すると、`add_source.py` の `process_url()` は無条件 `SKIP` ではなく `RECHECK` を返す。これを受けて Pass 1 はキャッシュ済み scratch ファイルを使わず必ず `markitdown` で実際に再フェッチし、フェッチ結果のハッシュを管理ファイルの現在の `source.hash`（上書き前の値）と比較する: 一致すれば内容は変わっていないと判断し、管理ファイルを一切書き換えず・Pass 2〜4 も実行せずに「変更なし」とだけ報告する。不一致であれば通常のソースと同様に Pass 1〜4 を最後まで実行し、Pass 4 の既存ルールが最終的な `status` を決定する。`status: pending` / `outdated` は従来通り `SKIP: already registered` のままで、この再フェッチは発生しない（既にキューに入っており次回実行で自然に処理されるため）。**`partial` は `failed_pages` で分かれる**（Issue #567）: 非空なら再試行の余地があり収集対象に残っているため `SKIP`、空なら同じ条件では二度と進展せず収集対象から外れているため `RECHECK` を返す — この場合に `SKIP` を返すと、その URL は鮮度を再確認する経路をどこにも持たなくなる（Step 0 の `SKIP` 分岐は Pass 1 へ進めるが、強制リチェック扱いにならないためキャッシュ済み scratch ファイルが使われる）。Issue #567 が収集条件を変えたことで生まれた穴であり、同じ Issue で塞いだ。
>
> **「非空だが無意味」な抽出結果の検出（Issue #425）**: Pass 1 の抽出失敗判定は当初「抽出テキストが空または読み取り不能」の場合のみを対象としており、JS実行が前提のSPAサイト（クライアントサイドレンダリングに依存し、`markitdown`・`curl`等の静的フェッチ手段では実際のページ内容を含まない「空シェル」しか返さないサイト）を静的フェッチした場合の「非空だが実質無意味」な結果を検知できなかった。`ai-driven-dev-wiki` パイロットで、`https://x.com/karpathy/status/1886192184808149383` の ソース管理ファイルが `status: generated`・`extracted_tokens: 1060` として成功記録されていたにもかかわらず、実際の抽出テキストはツイート本文を一切含まないナビゲーション・ログインプロンプト・埋め込みJSON状態等のシェルのみだったことが確認された。生成されたページの記述内容自体は他の有効なソースで裏付けられる事実だったため、`sources` に実体を伴わない一次資料URLが記録され続けるという来歴（provenance）の完全性が壊れる問題として顕在化した。`check_extraction_quality.py`（`docs/DesignDoc-ScriptSpec.md` 参照）が2つのガードを提供する: ガードB（`check-domain`）は `type: url`/`wikicommit` ソースの抽出前に、静的フェッチでは空シェルを返すことが確認済みの既知不可ドメイン（初期値: `x.com`/`twitter.com`/`music.youtube.com`）かどうかを判定し、該当すれば抽出を試みずに `status: failed` とする。ガードA（`check-density`）は全ソース種別の抽出成功後に、抽出テキストの自然文らしい文字の割合を判定する汎用ヒューリスティックで、ガードBがカバーしない未確認ドメインの同種の失敗を拾う安全網として働く。ガードBは `status: failed` として扱われ、`## Failure Reason` に理由が記録される点が既存の空/読み取り不能ケースと同じである一方、**ガードAはブロッキングではない**（Issue #562。当初は両ガードとも `status: failed` として同じ強度で扱っていたが、精度の異なる2つのガードを同じ強度で扱っていたこと自体が設計の混同だったという整理に改めた）。ガードBは「静的フェッチで空シェルを返すことが確認済み」のドメインに対する決定論的判定である一方、ガードAはテキスト形状のヒューリスティックであり、ガードAが本来検出したいJSシェル（ナビリンクの羅列＋埋め込みJSON/JS状態）は、リンクが多い正当な行政サイトや数値が多い正当な統計資料とテキスト形状のレベルでほぼ区別がつかない — `dev/pilot-saitama-wiki.md` では日本語Wikipedia・市公式サイト・統計PDFの計8件中4件が誤検知となり、実行者が4件すべてを手で上書きして続行していた。そのためガードAの `LOW_DENSITY:` は、対話実行時は人間に続行可否を確認する警告として提示し（続行した場合は Completion Notice に列挙する）、非対話実行時のみ従来どおり `status: failed` とする（誤検知の代償は1ソース分の再実行だが、真の空シェルを人間確認なしに通す代償は、実体を伴わない一次資料URLを `sources` に持つ幻覚ページであり、後者の方が大きいため。Pass 2b の Enter ベース承認が非対話実行でデフォルト却下に倒れた Issue #507 と同じ論点）。この2ガードとは**別軸**のチェックとして、取得前に「そもそも完全に取得できる環境か」を確かめるガードC（`check-fetch-capability`）が Issue #574 で追加された — `markitdown` は `youtube_transcript_api` が未導入だと YouTube 動画の字幕を例外も警告もなく落とし、タイトル・キーワード・Runtime・概要欄だけを返す。これは空シェル（ガードB）でも低密度（ガードA。実測で字幕あり 0.93 / 字幕なし 0.90 と差が出ない）でもない **partial extraction** であり、取得後のテキストからは検出できないため、既存2ガードのどちらを調整しても届かない。**この partial extraction は YouTube 固有の事情ではなく繰り返す失敗クラスである**（Issue #715 で確認）— 2 例目が GitHub の Issue / PR URL で出た（本文は取れるがコメントが全部落ちる）。原因は毎回違う（パッケージ不足・クライアント側レンダリング）が、形は同一で、いずれも「取得は成功し、取れた本文も本物で、ただし別の一部が欠ける」ため取得後のテキストからは見分けられない。3 例目が出たときに同じ調査を繰り返さないために書いておく: **既存 3 ガードのどれかを調整して届かせようとしないこと**。ガードA は落ちているものが自然文なら形状で区別できず（GitHub のコメントは自然文なので実測 0.37〜0.53 で余裕を持って PASS する）、ガードB は「空シェル」の定義に反し（本文は取れている）、ガードC は「パッケージを入れれば完全に取れる」ことを前提にしている。次に確かめるべきは、その欠落が**取得前に URL の形だけから決定論的に分かるか**であり、分かるなら下記の登録時通知に 1 行足せば済む。ガードCは該当ホスト（初期値: `youtube.com`/`youtu.be`/`m.youtube.com` の3ホスト。この3形式はリダイレクト解決後にいずれも `https://www.youtube.com/watch?…` に着地し、実測で同一の抽出結果になる）について必要パッケージの import 可否を確認し、未導入なら**処理全体を停止して `pip install` を案内する**（`status: failed` にはしない — 環境の問題であってソースの問題ではないため）。`music.youtube.com` はリダイレクトせず `YouTubeConverter` 自体が適用されない（パッケージを入れても解決しない）ためガードC ではなくガードBの既知不可ドメインとして扱う。ガードCの判定はホスト単位のため `/shorts/<id>`・`/playlist`・チャンネルページのような `/watch?v=…` 以外のURL形式は区別できない（これらも `YouTubeConverter` の前方一致要件を満たさず、フッターのナビリンクだけの数百文字になる。実測でガードAの比率は 0.40 で閾値を超えるため素通りする） — 取得後に抽出結果が `# YouTube` / `### Video Metadata` の形をしているかを Pass 1 手順6で確認し、していなければ `status: failed` とする。パッケージ導入済みで字幕が無い動画は「その動画に字幕が無い」という確定した事実なので、`status: failed` にせず Completion Notice にロールアップする。判定に使う「自然文らしい文字の割合」自体も、CJKの地の文がパーセントエンコードされたURLと1トークンに融合して道連れで捨てられていた実装バグを Issue #562 で修正している（詳細は `.claude/skills/wikicommit-generate/SKILL.md` Pass 1・`docs/DesignDoc-ScriptSpec.md`・`docs/DesignDoc-skills.md` §11.6 参照）。`wikicommit-collect` の候補提示ステップ（§6.1 冒頭の Ingest フローとは別の、テーマに基づく候補探索フロー）もガードBの既知不可ドメインリストを参照し、候補提示の時点で除外する — free-exploration経由で一度除外されたソースが再度候補として提案されてしまう再侵入を防ぐため。
>
> **partial extraction はガードではなく登録時の通知で扱う（Issue #715）**: GitHub の Issue / PR の URL を `type: url` として登録すると、**本文だけが取れてコメントが全部落ちる**。公開 Issue 3 件の実測で、API 上のコメント数は 3 / 6 / 3 件、抽出結果に含まれていたコメントはいずれも 0 件、一方で本文は 3 件とも取れていた。失敗にはならず `status: generated`・`extracted_tokens` 非ゼロで**成功として記録される**。上の #574 が定義した partial extraction の 2 例目である。
>
> **3 ガードのどれにも足さない（Issue #715 の対応方針 (c) を採用）**。理由はガードごとに異なる:
>
> | | なぜ足さないか |
> |---|---|
> | ガードB（`check-domain`） | 定義に反する。あの表は「静的フェッチで**空シェル**を返すことが確認済み」のドメインを持つが、ここでは本文が取れている。加えてブロックすると、本文だけで十分なソースまで `status: failed` になり `wikicommit-merge` Step 9 が `wikicommit-generation-failure` の追跡 Issue を立てる — Issue #567 が `partial` について指摘した「誤った記録が残る」形そのもの |
> | ガードA（`check-density`） | 落ちているのが自然文なので形状では区別できない（実測 0.37〜0.53 で閾値 0.3 を上回る）。閾値調整で解ける問題ではなく、上げれば Issue #562 が実測した誤検知 4/8 件を悪化させるだけ |
> | ガードC（`check-fetch-capability`） | 前提が満たされない。あの表は「そのパッケージを入れれば `markitdown` が完全に取れる」ことを前提に `importlib.util.find_spec()` で判定するが、GitHub に必要なのはパッケージではなく**別の取得経路**であり、`gh` を入れても `markitdown` の取得経路は変わらない。ここを一般化すると、exit 1 の意味（処理全体を止めて `pip install` を案内する）が GitHub に対して端的に誤りになる |
>
> **採ったのは `add_source.py` の登録時通知**で、ShareAlike ソースの注意書き（Issue #570）と同じ形である。判定はホストとパスの形だけで決まる決定論的なもので（`github.com` の `/{owner}/{repo}/issues/{n}` と `/pull/{n}`）、ブロックせず・`status` を変えず・取得も止めず、登録時に一度だけ「コメントは取り込まれない」と知らせて判断を人間に委ねる。**止めるのが正しくないのは、本文だけで十分なソースが実在するからである** — Issue 本文がまさに欲しいものである場合はこの URL で正しく、そこで止めると正当な用途を潰す。**欠陥だったのは部分的な結果そのものではなく、それが黙って起きることだった。**
>
> 表の置き場は `check_extraction_quality.py` ではなく `add_source.py` とした。あちらの 2 つのホスト表はいずれも Pass 1 の分岐（取得するか・`status: failed` にするか）を左右する**ガード**であり、そこに非ガードを混ぜることは、精度の異なるものを同じ強度で扱っていた Issue #562 の混同を作り直すことになる。`add_source.py` は既に `KNOWN_SOURCE_LICENSES` という「登録時に決定論的なホスト単位の事実を記録・通知する表」を持っており、そちらが正しい類例である。
>
> **`KNOWN_JS_SHELL_DOMAINS` の「確認済みのものだけを表に持つ」規則はそのまま持ち込まない**。あちらは誤ったエントリが取得自体を飛ばすため実害があるが、こちらの誤りは余計な注意書きが 1 行出るだけであり、非対称の向きが逆である。したがって `/issues/` は直接実測し、`/pull/` は GitHub が同一のコメントタイムラインを描画することを根拠に含めた（本 Issue の実測は Issue のみ。セッションのネットワークが自リポジトリ外の github.com へ出られないため PR の再実測は行っていない）。**`/discussions/` は意図的に含めていない** — 同じくコメント欄を持つが別のプロダクト面であり、機構レベルの根拠が無いまま推測で足すことはしない。`github.com` を丸ごと対象にもしない: README・blob・release の取得は実際に完全であり、最も多い GitHub URL の形に誤った注意書きを出すことになる。
>
> **`gh` 経由の取得経路は作らない**。本 Issue の対象は「今の経路が黙って壊れること」に限り、`gh` 経路を作ることは Issue / PR の取り込みを**機能として設計する**ことにあたる（Issue #715 が明示的にスコープ外とした範囲）。未解決の論点が 3 つあり、いずれも別の設計を要する: (1) **認証の前提** — `gh auth` が通らない環境では使えず、取得の可否が利用者ごとに変わる。`add_source.py` は `.wikicommit/scripts/` からの import すら持たない自己完結スクリプトであり、外部 CLI への依存はその設計とも噛み合わない、(2) **hash の意味** — Issue はコメントが増え続ける living resource であり、hash が毎回変わって `outdated` が立ち続ける（`docs/DesignDoc-skills.md` Pass 2a は既に living resource を source-as-entity から除外している）。Closed / Merged に限れば実質凍結されるが、その線を引くこと自体が設計判断である、(3) **議論は覆る** — コメントには撤回された案・誤った前提が混ざっており、そのままページ化すると Pass 4 が「ソースに書いてある」として通してしまう。Issue #553 / #564 が繰り返し確立した「消費者と同時に足す・受け皿だけ先に作らない」に従い、取り込みを機能として設計する段で扱う。なお `source.type` は仮に経路を作るとしても `type: url` のままが正しい（Issue #352 が確立した「`source.type` はコンテンツの種類ではなくソースをどう識別するかで分ける」という軸に従えば、取得経路の分岐は `source.type` に出さない）。
>
> **`wikicommit-collect` の候補提示には注記を出さない**。同 Skill は候補 1 件あたりの subprocess 呼び出し数と一覧の可読性を明示的に予算として管理しており（`check-domain` とライセンス照会の 2 回）、3 回目を足すことになる。そしてこの事実は候補の**可否を変えない** — `check-domain` と違って候補を落とせないため、フィルタとしては何もしない。人間が選んだ候補は Step 8 が `wikicommit-generate` Step 0 経由で登録するので、通知はそこで確実に届く。Issue #646 が ShareAlike を候補提示まで前倒しした先例はあるが、あちらの帰結は**公開後は取り返しがつかない法的義務**であるのに対し、落ちたコメントスレッドはそうではない — 登録後に気づいてもソースを外せば済む。

### 6.2 Merge（`/wikicommit-merge`）

> **ブランチ命名規則（例外）**: `wikicommit/merge-<YYYYMMDD>-<HHMMSS>` 形式。CLAUDE.md の `issue-NNN` 規約は Issue 駆動の開発ブランチ向けであり、`/wikicommit-merge` が自動生成する一時的なブランチには適用しない。

#### 処理フロー

```
.wikicommit/ 配下の未コミット変更（Wiki ページ・管理ファイル・index.md）を検出
  ↓ 変更なし → 「マージ対象がありません」と表示して終了
品質チェックを実行（順次）:
  # 変数定義（以下のコマンド呼び出しで使用）
  # <変更 .md ファイル>    = git diff --name-only -- '.wikicommit/entity/**/*.md' で取得した変更ファイルのパス一覧
  # <削除対象ファイル>     = 上記のうち、git show HEAD:<path> で旧 frontmatter を確認して旧 status が removed でなく
  #                          現 status が removed であるファイルのパス一覧（削除フロー判定。存在しない場合は --deleted を省略）
  # <新規ソースファイル>   = 変更された .wikicommit/source/**/*.md（削除された管理ファイルは除く）の
  #                          source.path（source.type: path のみ）のうち、git status --porcelain で
  #                          `??`（untracked）と判定されたパスの一覧（Issue #106。既に追跡済みの
  #                          既存ファイルや、追跡済みだが未コミットの変更があるファイルは含めない）。
  #                          `.gitignore` 除外・非 ASCII パス・glob メタ文字を含むパスのいずれでも
  #                          誤判定しない（Issue #115。具体的な git コマンドは SKILL.md ステップ 2 の 3. 参照）
  python .wikicommit/scripts/validate_frontmatter.py <変更 .md ファイル>
  python .wikicommit/scripts/check_wikilinks.py --changed <変更 .md ファイル> [--deleted <削除対象ファイル>]
  lychee --config .lychee.toml                        # 外部リンク検証（sources URL・本文 https://）
  markdownlint-cli2 <変更 .md ファイル>               # スタイル検証（warning のみ）
  python .wikicommit/scripts/check_orphans.py         # 孤立ページ・重複ページ検出
  ↓ blocking エラーあり → エラー内容を表示して中断
  ↓ warning のみ → 内容を表示してユーザーに続行確認
ブランチ作成（wikicommit/merge-<YYYYMMDD>-<HHMMSS>）
  ↓
変更ファイルと <新規ソースファイル> をコミット
  ↓
PR 作成 → `mergeStateStatus` が `CLEAN` になるまで `gh pr view --json state,mergeStateStatus` でポーリング（最大 300 秒・10 秒間隔。Phase 2 以降は lychee による外部リンク検証に数分かかるため） → `--auto` なしで `gh pr merge --squash`
  ↓ `state: CLOSED` または `mergeStateStatus` が `DIRTY`/`BLOCKED`（待っても解消しない終端状態） → 即座にポーリングを打ち切りエラー表示して中断
  ↓ 上記以外でタイムアウト → エラーを表示して中断（マージしていない以上、次のレビュー追跡 Issue 作成へは進まない）
                   残存ブランチ・PR のクリーンアップ手順: `gh pr close <PR番号>` → `git push origin --delete <ブランチ名>` → /wikicommit-merge を再実行

> **`gh pr merge --auto` に依存しない理由（Issue #456）**: GitHub の auto-merge 機能（`--auto` がフォールバックする `enablePullRequestAutoMerge` ミューテーション）は、リポジトリの `allow_auto_merge` 設定に依存する。この設定は GitHub Free の private リポジトリでは CLI/API/UI いずれからも有効化不可能（バグでも設定漏れでもなくプラン制限）であり、`wikicommit-merge` が想定する主要ユーザー像（GitHub Free で private wiki を運用する個人）で構造的に失敗しうる。`wikicommit-merge` は PR 作成前にローカルで品質チェックを完了させる設計のため、そもそも「チェック通過を待つ」auto-merge 機能を必要としない。必要なのは GitHub 側の `mergeStateStatus` 計算が終わるまでの数秒を待つことだけであり、これはプランに関係なく参照できる。`review-issue-close-sync.yml`（後述の Issue Close 検知後の自動処理）の "Auto-merge on quality pass" ステップにも同じ変更を適用している。
  ↓（PR マージ確認後）
レビュー追跡 Issue を Wiki ページ単位で作成（review_status: pending のページのみ。Issue #313 — 旧「後レビュー用 PR」方式を置き換え）:

  ※ 既に同じページを指す open な `wikicommit-review` ラベル Issue が存在するページはスキップ（`gh issue list --label wikicommit-review --state open --json number,body` を取得し、`body` を機械可読マーカーで局所的に照合する。`gh issue list --search` には頼らない — GitHub の検索インデックスがこの形式の HTML コメントをどう扱うかの保証がなく、取りこぼすと重複 Issue を作ってしまうため）
  ↓
生成失敗トラッキング Issue を ソース管理ファイル単位で作成（`.wikicommit/source/` 配下で `failed_pages` が空でない管理ファイルが対象。Issue #452 — 上記レビュー追跡 Issue と同じ全件走査・マーカー埋め込みパターンをそのまま踏襲するが、対象は「生成されたが未レビューのページ」ではなく「生成自体が失敗し何も書き出されなかったソース」で、ラベルも別（`wikicommit-generation-failure`）。Close しても `review_status` のような自動書き換えは走らない可視化専用の記録用 Issue — 再試行するには `/wikicommit-generate` を再実行する）
  ↓（GitHub Actions により自動実行。Phase 2 以降）
```

#### レビュー追跡 Issue 本文テンプレート

対象ページの frontmatter がどの出自フィールドを持つかでテンプレートを3分岐する（Issue #525）: `translated_from`（翻訳ページ・`wikicommit-translate` 出力）、`derived_from`（合成ページ・`wikicommit-synthesize` 出力、Issue #283）、どちらも無し（通常の `sources` ベースページ）。この3フィールドはページごとに排他（§4.2）のため、常にいずれか1つの分岐が適用される。翻訳ページは `sources` を持たず出自を `translated_from` から継承する設計（§4.2）のため「内容がソース元文書と一致しているか」がそのまま意味を持たず、`generated_at`/`generated_by` の代わりに `translated_at`/`translated_by` を持つ。合成ページは `sources` の代わりに `derived_from`（`{path, source_commit}` の配列）を持つが、`generated_at`/`generated_by` は非翻訳ページと同様に持つ — 変わるのはレビュー対象・「読んだら」の内容のみ。「操作方法」は3バリアントで共通（`review-issue-close-sync.yml` の Close 検知時の挙動を説明するだけで、ページの出自に依存しないため）であり、ラベル（`wikicommit-review`）とマーカー形式も共通のため、`review-issue-close-sync.yml` 側の変更はいずれの分岐についても不要。

> **本文は `primary_lang` で描画する（Issue #773）**: 3 バリアントとも SKILL.md 上のテンプレートは英語だが、`/wikicommit-merge` Step 8 は書き出し時にこれを `config.yml` の `translation.primary_lang` で描画する（`en`・値なし・ファイルが読めない場合は英語のまま）。**公開サイト側には切り替えがあるのに、ここには無かった** — バナー・出典ボックス・ビルド生成ページはいずれもページの言語で描画される一方、読者向けの面で追跡 Issue だけが言語を持たなかった。日本語 Wiki の運用者にも、日本語ページ 1 枚につき英語の Issue が 1 件届いていた。
>
> **本バッチの Issue #770（スクリプトのコンソール出力）・Issue #772（CHANGELOG）とは逆を向くが、規則は同じ「読み手で決める」である**。あの 2 つの読み手は運用者とエージェントであり診断であるため固定英語、こちらの読み手は Close する人であり、Issue #313 の設計意図により**公開 Wiki を読むだけで Claude Code のセッションを持たない人**を含む。3 件をまとめて読むと線引きが見える。
>
> **`.github/ISSUE_TEMPLATE/report.md` は同じケースではなく英語のまま**。あちらは自分でその理由を書いている — リポジトリに 1 つしかないので**自分の言語を持てない**。追跡 Issue はページ 1 枚につき 1 件で、そのページには `lang` があるため、同じ論法が逆の結論を出す。
>
> **ページの `lang` ではなく `primary_lang` を使う**（Issue #773 の検討事項 2）。追跡 Issue はページ 1 枚を追うのでページの言語が直感的に見えるが、読むのは Close 権限を持つ人であり、それはページではなくリポジトリの性質である。`targets` を持つ Wiki でページの `lang` を使うと、同じ 1 人の運用者に 2 言語の Issue が届く。
>
> **翻訳しないもの**: マーカー行（`<!-- wikicommit-page: ... -->`。機械が読む唯一の部分で、`review-issue-close-sync.yml` が完全一致で照合する）・Issue タイトル（識別子であり、一覧での並びと検索性がその形に依存する）・実際に打つ／目で追う文字列（コマンド名・パス・frontmatter のキーと値・ラベル）・フィールドの値そのもの（ページパス・日付・モデル ID、および値が無いときに書く literal な `unknown`）。見出しと散文は翻訳する。
>
> **共通の「操作方法」セクションも翻訳する**。下記の「全バリアントでそのまま挿入する」が言っているのは 3 バリアントで同一の文面を使うことであって、このセクションだけ英語で残すことではない。ここを英語のまま残すと、この変更が対象にしている読み手（Claude Code のセッションを持たずに Close する人）に対して、Close に権限が要ること・修正依頼のコメントだけでは直らないこと・コメントが先へ渡る 2 つの例外という、最も操作に直結する部分だけが読めない言語で届くことになる。
>
> **`review-issue-close-sync.yml` は変更していない**（マーカーしか読まない契約は不変）。`tests/test_tracking_issue_checklist.py` も無改修 — アサートしているのは SKILL.md のテンプレート本文であって、生成された Issue ではない。
>
> **実行のたびに言い回しが揺れる**（テンプレートを LLM が描画するため）。各 Issue は一度しか読まれないため許容する — UI 文字列と違い、揺れが 2 つ並んで見えることがない。**既に立っている open な Issue への遡及は行わない**（新旧混在を許容する慣例）。**`primary_lang` が ja/en 以外の Wiki での実地確認はしていない**（描画は LLM が行うので言語の制約は無い）。

##### 共通の「操作方法」セクション（全バリアント共通）

以下を「## 読んだら」とマーカー行の間に、全バリアントでそのまま挿入する:

```markdown
## 操作方法

この Issue を Close するには、このリポジトリへの書き込み権限（Organization 所有のリポジトリでは triage 権限）が必要です。自分が立てていない Issue を Close できるのはリポジトリのオーナー・コラボレーター・triage 権限以上を持つ人に限られ、それ以外の閲覧者には Close ボタン自体が表示されません。権限を持たずにこのページの誤りを指摘したい場合は、代わりにご自身で新しい Issue を立ててください。自分のアカウントで立てるだけなので権限は不要で、その内容は `/wikicommit-fix` が読み取ります。公開済みの Wiki であれば、ページ上部のバナーにある報告リンクが、対象ページを埋めた状態でこれを行います（このリンクの文言はページの言語に従うため、日本語ページでは「気づいた点を報告する」と表示されます）。
ページ本文を読んで問題なければ、この Issue を Close するだけで構いません。`.github/workflows/review-issue-close-sync.yml`（Issue #313）が Close を検知して `review_status` を `reviewed` に書き換え、品質チェック通過後に自動マージします。Approve というPR操作は不要で、GitHub の Web/モバイル UI から Close するだけで完結します。
修正が必要な場合は先にページを修正（`/wikicommit-fix` 等）してから、この Issue を Close してください。
**受け取ったこと・気づいたことをコメントに書くのは、この Issue の目的そのものです** — それ以上何もする必要はありません。
**ただし「直してほしい」というコメントは、それだけでは直りません** — Close 時に自動実行される処理はこの Issue 本文末尾のマーカー行のみを読み、コメントの中身は一切参照しないため、修正依頼を書いただけで Close するとその修正は行われないままマージされます。実際に反映させるには `/wikicommit-fix <このIssueのURL>` を明示的に実行してください（Issue の本文とコメントの両方を読み取って修正案を提示します）。修正が反映されてからこの Issue を Close してください。
**2 種類のコメントだけは例外です。どちらもページ本文ではなくソースについての話であり、`/wikicommit-fix` はソースに一切触れられないためです。**
**ページが本来書かれるべきだった文書の URL** — `/wikicommit-generate <url>` を実行し、続けて `/wikicommit-merge` を実行してください（その文書の内容は、それを元に書かれたページへ統合され、そのページが再び読まれるのを待つ状態に戻ります。この Issue が翻訳ページ・合成ページを追跡している場合、それはこのページではなく出自元のページです）。それらを実行できない場合でも、コメントに URL を残せば実行できる人に渡ります — ただし登録が済むまでこの Issue は Close しないでください。Close するとこのページはそのまま `reviewed` として確定します。
**ソース自体が誤っているという指摘** — こちらがもう 1 つです。この判断に到達できる自動チェックは 1 つもありません。この Wiki の検査はすべてソースを「ページを測る基準」として扱うため、**ソースの誤りを忠実に写したページは全部の検査を通ります**。どのソースの何が誤っているかをコメントに書いてください。書き込み権限を持つ人がその管理ファイルに `status: retracted` と理由を書き、`/wikicommit-status` がそのソースに立っている全ページを列挙します。挙げるのはこのページ自身が書かれた元の文書だけにしてください — この Issue が翻訳ページ・合成ページを追跡している場合、このページは自分のソースを持たず、その文書は出自元のページに属するため、指摘先はそちらになります。反映されるまでこの Issue は Close しないでください（理由は上と同じです）。
```

> **Close には権限が要ることを明記する（Issue #665）**: 旧文面は「Close するだけで完結します」「GitHub の Web/モバイル UI から」とだけ書いており、**権限を持たない読者に対しては、できないことをできると案内している状態**だった。レビュー追跡 Issue は `wikicommit-merge` Step 8 が自動生成するもので閲覧者本人の Issue ではないため、Read しか持たない読者には Close ボタンが出ない。`review-issue-close-sync.yml` のコメント自身が "closing an Issue you didn't open just requires repo write access" と書いており認識はあったが、それは「PR 承認より制約が緩い」という比較の文脈で、不特定多数の読者に対する案内としての妥当性は検討されていなかった。
>
> **前提の裏づけ**: GitHub 公式ドキュメントのソース（`github/docs` リポジトリの `content/issues/tracking-your-work-with-issues/administering-issues/closing-an-issue.md` の `permissions:` フロントマター）が次のとおり明記している — "Anyone can close an issue they opened. / Repository owners, collaborators on repositories owned by a personal account, and people with triage permissions or greater on repositories owned by an organization can close issues opened by others."。個人アカウント所有のリポジトリには triage ロールが無いため、この場合の条件は実質的にコラボレーター（write）となる。**別アカウントでの実地確認は行っていない**（本セッションに第 2 のアカウントが無いため）。Issue #403 の `closed_by` は「公式ドキュメントに記載の無い webhook ペイロードの挙動」だったのに対し、こちらは公式に文書化された権限モデルそのものであり、性質が異なる。
>
> 代替経路として案内するのは「自分で新しい Issue を立てる」ことそのものであり、公開ページの報告リンク（`WikiCommitBanner` が `review_status` に関わらず常時表示する。Issue #245）はその近道として併記するに留める。自分で立てる Issue なので権限の壁が無く、その内容は `/wikicommit-fix <issue-url>` が読み取る。**参加募集の文言にはしない** — 外部レビュアーを募る段階ではないため、加えるのは「この操作には権限が要る」という事実と代替経路の提示に留める。
>
> **報告リンクを主たる代替経路にせず、ラベル文字列も verbatim で引用しない理由**（実装との突き合わせで判明した 2 点）: (1) このリンクとその裏づけである `.github/ISSUE_TEMPLATE/report.md` は `_root_outputs.py` 上いずれも `QUARTZ` 限定で配布される一方、レビュー追跡 Issue を生む `review-issue-close-sync.yml` は `ALL` である。つまり `--quartz` なしで init した Wiki には**バナー自体が存在しないのに追跡 Issue だけが立つ**ため、報告リンクを唯一の代替経路として書くと、その構成の読者には存在しない導線を案内することになる。「自分で Issue を立てる」は構成を問わず常に成立する。(2) リンクのラベルは `WikiCommitBanner` が `resolveLocale(frontmatter.lang, cfg.locale)` で解決するロケール依存の文字列（`ja-JP.ts` では「気づいた点を報告する」。Issue #738 で「誤りを報告する」から改めた）である一方、Issue 本文テンプレート（`wikicommit-merge` SKILL.md）は常に英語で verbatim 挿入される。英語の Issue 本文に `"Report something you noticed"` と書くと、日本語 Wiki の読者はページ上にその文字列を見つけられない。そのため機能で説明し、ラベルが言語に従うことを一言添える形にした。
>
> **権限の層は直ったが、アカウントの層が残っていた（Issue #742）**: 上の代替経路（自分で新しい Issue を立てる）と、その近道である公開ページの報告リンクは、どちらも**読者が GitHub アカウントを持っていること**を前提にしている。したがってアカウントを持たない読者には経路が 1 本も存在しない一方、`WikiCommitBanner` はその読者にも報告リンクを常時表示していた（Issue #245）— 本 Issue が直したのは #665 と**まったく同じ形の誤り**（できないことをできると書いている状態）が 1 層下に残っていたことである。実測すると、未ログインで `/issues/new?template=…&title=…&body=…` を開くと `login?return_to=<元 URL 全体>` へ飛ばされてフォームは一切見えない。**ただし事前入力は失われない** — `return_to` に `template=` / `title=` / `body=` を含む元 URL が丸ごと入っており、認証後にそのまま復元される。この 2 点目のおかげで本 Issue の範囲は狭くなり、残る欠陥は「リンクが予告なくログイン壁に着地すること」だけになった。したがって対応も、バナーの報告リンクの隣に「GitHub アカウントが必要」という事実を 1 つ添えるに留めてある（`ja-JP.ts` / `en-US.ts` の `reportLinkAccountNote`）。**アカウント不要の受け皿は作らない** — 外部サービスは「外部 DB を持たない」設計に反し、スパム対策と個人情報の受領という別種の運用を生む。**参加募集の文言にもしない**のは #665 と同じ線引きであり、加えるのは事実の 1 行のみである。文言をリンクのラベル自体に折り込まなかったのは、ラベルが `.wikicommit-banner__link` として下線付き・色付きで描画されるためで、注記まで同じ強さで出すと行動の呼びかけと競合する（Issue #738 と共有する「バナーの視覚的な重さを増やさない」制約）。この Issue 本文テンプレート側には何も足していない — 上記 (1) のとおりバナーを持たない構成（`--quartz` なしで init した Wiki）が存在し、そこでは案内する対象そのものが無いためである。

##### `sources` ベースページ（`translated_from` も `derived_from` も無し）

```markdown
## レビュー対象

- ページ: `.wikicommit/entity/<lang>/<Type>/<slug>.md`
- 生成日: <generated_at>
- 生成モデル: <generated_by>

## 読んだら

読んだら、**このページから何を受け取ったか**を一言だけコメントに書いて Close してください（Close 時のコメント欄にそのまま書けます）。要約でなくて構いません。「ここが意外だった」「既に知っていることばかりだった」でも十分です。

**これは理解度のテストではありません。** このページの知識が実際に人に渡ったことの記録です。Close が述べるのはそれだけであり、ページが正しいことではありません。

このページは生成時に、書き起こしの元になった資料と機械が照合済みです（公開ページ上部に表示されている場合は、そこにモデルと日付が出ます）。以下はどの自動チェックも見ていないので、読んでいて気づいたことがあれば同じコメントに書いてください。**探しに行く必要はありません。**

- 実在の人物・組織について、書きすぎ・断定しすぎに感じた箇所、係争中の主張が確定事実として書かれている箇所、記録する理由の無い私的な事柄。このページを作るかどうかは生成時に `.wikicommit/entity-policy.md` に照らして判断済みだが、**その中の記述は誰も見ていない**
```

> **なぜ PR ではなく Issue か（Issue #313）**: 旧方式（`review-pr-auto-merge.yml`、Issue #281）は後レビュー用 PR への Approve を自動マージのトリガーとしていたが、**GitHub は PR 作成者本人によるその PR への Approve を許可しない**。後レビュー用 PR は常に Wiki 運用者自身のアカウントで作成されるため、一人でWikiを運用しているユーザー（WikiCommit が想定する主要ユーザー像の一つ）はそもそも Approve ボタンを押せず、この仕組みは一度も機能しないまま終わっていた。GitHub の Issue Close にはこの「自己承認禁止」制約が存在しない（Issue を開いた本人であっても、リポジトリへの書き込み権限があれば問題なく Close できる）ため、これに置き換えた。**ページ単位であること自体は、GitHub の制約より前に設計原則の帰結である** — `docs/DesignDoc-architecture.md` §1.6「レビューは分割可能でなければならない」は、1 ページが独立してレビュー・承認できる最小単位であること（1 ページ ＝ 1 Issue ＝ 1 Close）を要求する。上の経緯（自己 Approve 禁止が入口だったこと）は事実としてそのまま残すが、**旧方式が仮に機能していたとしても**、バッチ 1 件に PR 1 本という単位は §1.6 を満たさない: LLM は 1 人が読める速さを超えてページを生成するため、レビューを人で割れない設計は生成が速いほど詰まる。したがって Issue 化は制約への回避策であると同時に、正しい単位への移行でもあった。その帰結として、Claude Code のセッションを持たない人でも、リポジトリへの書き込み権限（Organization 所有のリポジトリでは triage 権限）さえあれば GitHub 上で直接 Close するだけでレビューできる。**権限を持たない読者はこの Close ができない** — その場合の経路は上記の共通「操作方法」セクションのとおり自分で新しい Issue を立てることであり、そこが `/wikicommit-fix` の入口になる（Issue #665）。
>
> 経路A の一括PR（Step 6 で作成する PR）は本 Issue の対象外で変更なし（個別の人間承認を要求しない設計のまま）。経路B（`wikicommit-review`）も対象外で変更なし（人間がローカルで Skill を実行した時点でそのセッションの git author 情報が既に人間本人になっているため、追加の仕組みなしで「誰がレビューしたか」が既にコミットに残っている）。
>
> **Issue Close 検知後の自動処理**: `.github/workflows/review-issue-close-sync.yml`（`/wikicommit-init` が配布。Quartz 選択の有無に関わらず常に配布される — 後レビューフローは publish 方式に依存しないため）が `issues.closed` イベントをトリガーに、ラベルが `wikicommit-review` の Issue のみ処理する。Issue 本文のマーカーからページパスを取得し、main 上でそのページが実在し `review_status: pending` のままであることを確認（既に `reviewed` 済み・ページ削除済みならば no-op — 冪等性の担保。Issue の再オープン→再クローズや、`pull_request_review` が複数回発火しうる旧方式と同じ配慮）した上で `wikicommit/review-<lang>-<Type>-<slug>` ブランチを作成し、`review_status` を書き換えてコミット（`Reviewed-by: <Issueをcloseした人の表示名> <<login>@users.noreply.github.com>` トレーラー付き。`github.event.issue.closed_by` から機械的に取得。詳細は §6.7）、PRを作成して `validate_frontmatter.py` / `check_wikilinks.py` の品質チェックPASSのみを条件に自動マージする（経路Aの一括PRと同じ信頼レベル。追加の人間承認は要求しない）。
>
> **マージ後の GitHub Pages 再ビルドは明示的な `workflow_dispatch` で起動する（Issue #544）**: GitHub Actions には「既定の `GITHUB_TOKEN` によって発生した push イベントは、他のワークフローの標準トリガー（`push` / `pull_request` 等）を起動しない」という仕様上の制約がある（無限ループ防止のための意図的な挙動）。`review-issue-close-sync.yml` の squash merge はまさにこれに該当するため、`on: push` でトリガーされる `deploy.yml`（Quartz ビルド → GitHub Pages 公開。§8）はレビューマージ後に一度も自動起動しなかった。結果として、`main` 上のページは `review_status: reviewed` になり `wikicommit-status` もリポジトリ上のソースも正しい状態に見える一方、**公開サイトだけが未レビューバナー付きの古い状態で取り残され、その食い違いに気づく手段が無い**（`wikicommit/ai-driven-dev-wiki` で実地確認。レビューマージの7時間以上前を最後に `deploy.yml` が一度も走っていなかった）。
>
> `workflow_dispatch` / `repository_dispatch` はこの制約の明示的な例外として文書化されており、`deploy.yml` は元から `workflow_dispatch:` トリガーと `github.event_name == 'workflow_dispatch'` を許す `build` ジョブの `if:` を備えている。そこで `review-issue-close-sync.yml` の自動マージ成功後に `gh workflow run deploy.yml --ref <default branch>` を実行するステップを追加した。このステップは `deploy.yml` が存在しないリポジトリ（`--quartz-pages` を選ばなかった場合。`review-issue-close-sync.yml` 自体は publish 方式に依存せず常に配布される）では何もせずに終了する。dispatch に失敗した場合は warning ではなく **error でジョブを失敗させる** — 静かに取りこぼすと、このステップが解消しようとしている状態（`main` は reviewed・公開サイトは未レビュー・気づく手段が無い）がそのまま再現してしまうため。dispatch には `actions: write` 権限が必要で、同ワークフローの `permissions:` ブロックに追加している。
>
> この抜け穴は `wikicommit-merge`（経路Aの一括PR・経路Bの `wikicommit-review`）が人間自身のトークンで `main` に push する場合には発生しない（通常の push イベントとして扱われ `deploy.yml` が正常に起動する）。`review-issue-close-sync.yml` 経由の自動マージに固有の問題である。
>
> **採らなかった案**: (a) `gh api repos/{owner}/{repo}/pages/builds -X POST` で Pages ビルドを直接キックする — Quartz によるサイト生成自体は `deploy.yml` の責務であり、この API は生成済みの成果物の公開を叩くだけなので本質的な解決にならない。(b) 個人アクセストークン（PAT）でマージして `GITHUB_TOKEN` の制約自体を回避する — 配布 Skill として誰でも使える設計を保つには追加の PAT セットアップ手順をユーザーに要求することになり、`wikicommit-init` の導入コストを上げる。
>
> **未決事項として残す範囲**: レビュー追跡 Issue が Close 後に再オープンされた場合、`review_status` を `reviewed` から `pending` に自動で戻す仕組みは用意しない（Issue #313 の完了条件で意図的に未決事項とした）。再レビューが必要になった場合は人間が手動でページの `review_status` を書き換える。

### 6.3 Review

#### 経路 A: 自動生成フロー

```
/wikicommit-generate → ローカルに Wiki ページ生成（review_status: pending で出力）
  ↓
/wikicommit-merge → 品質チェック → PR → 自動マージ → レビュー追跡 Issue 作成（Issue #313）
  ↓
レビュー追跡 Issue（wikicommit-review ラベル）の内容を GitHub 上、または /wikicommit-review 経由で確認
  ├─ 問題なし → Issue を Close（review-issue-close-sync.yml が検知して review_status を reviewed に書き換え、
  │              品質チェック通過後に自動マージ。Issue #313）
  └─ 問題あり → ページを修正（/wikicommit-fix 等）→ 修正が main に反映されてから Issue を Close（同上、自動マージ）
     ※ 既に reviewed のページを /wikicommit-fix が書き換えた場合は review_status が pending へ戻る（Issue #724）
```

#### 経路 B: 人間起点・修正フロー

```
.wikicommit/entity/ にページを手動作成・編集
  ↓
/wikicommit-review（任意だが推奨）
  [1] frontmatter 補完（必須フィールドが欠けていたら LLM が補完提案）
  [2] sources チェック（なければ type: manual の設定を促す）
  [3] 整合性チェック（sources: がある場合、hash と sources.path の実ファイルを比較し不一致を指摘）
  [4] sources を再取得し、独立した事実確認を実施（Issue #455 — DesignDoc-pipeline.md §6.2 が人間に示す観点に沿って所見を出力する。全文再掲はデフォルトでは行わず、ソースが取得できない場合や人間が希望した場合のみのフォールバックとする）→ 所見を提示し人間に明示確認を求める（Issue #313 — 構造チェック通過だけでなく実際にレビューしたことを担保する）
  [5] 対応するレビュー追跡 Issue の有無を確認（経路B は通常無い）→ 無ければ review_status: reviewed をローカルに書き込む
  ↓
/wikicommit-merge → 品質チェック → PR 作成（review_status: reviewed の変更を含む） → 自動マージ
  （review_status: reviewed のページはレビュー追跡 Issue 生成の対象外）
```

`/wikicommit-review` は経路Aのページ（レビュー追跡 Issueが存在するページ）に対しても使える。その場合はステップ[5]で対応する Issue が見つかるため、ローカルに書き込む代わりに `gh issue close` でその Issue を Close する（詳細は下記 review_status 遷移表、および `.claude/skills/wikicommit-review/SKILL.md`）。

#### 内容が書き換わったページは `reviewed` のまま残さない（Issue #724）

`reviewed` と `reviewed_by`（Issue #663）は「この文章を人間が読んだ」という主張であり、ページの内容が書き換わればその主張は事実でなくなる。ページを書き込む 6 経路のうち 4 つ（`action: create`・`--regenerate`・`wikicommit-translate`・`wikicommit-synthesize`）は元から `pending` を書いていたが、残る 2 つがそうしていなかった:

| 経路 | 旧挙動 | 現挙動 |
|---|---|---|
| `wikicommit-generate` Pass 3 の `action: update` | `reviewed` を無条件に維持 | 内容が変われば `pending`（Pass 4 step 6 がスクリプトを実行） |
| `wikicommit-fix` | 規則が無く、触れていなかった | 同上（Step 5 でスクリプトを実行） |

**`wikicommit-fix` の方が鋭い。** この Skill は「レビュー済みの内容が誤っていた」から起動されるものであり、しかも公開ページの報告リンクは `review_status` に関わらず常時表示される（Issue #245）ため、`reviewed` なページの誤りを読者が報告するのは設計上の主経路である。結果として、**そのレビューが見落としたからこそ書き直された文章に、レビュアーの実名が付き続けていた**。加えて Step 8 は `pending` のページにしか追跡 Issue を作らないため、更新された `reviewed` ページは恒久的に再レビューされない終端状態になっていた。

**「常に `pending` に戻す」は採らない。** 取り込みを続ける Wiki ではページが `reviewed` と `pending` を往復し、そのたびに追跡 Issue が立つ — レビュー負荷が青天井になり `reviewed` が到達不能になる。信頼ラダーの価値は上段に**届くこと**にも依存している。代わりに §6.1 の再生成モードが持つ unchanged-output valve と同じ形を使い、**内容が実際に変わったか**で判定する。判定は決定論的スクリプト `reset_review_on_content_change.py`（`docs/DesignDoc-ScriptSpec.md`）に委譲する — 完全に決定論的に判定できる操作を instruction として書くと非決定論的な失敗モードを持ち込む（Issue #474）うえ、本件は「人間のレビューが要るか否か」を左右する判定である。

線引きは 6 フィールドの ignore リスト（`generated_at` / `generated_by` / `generated_with` / `review_status` / `reviewed_by` / `sources[]`）で、それ以外の frontmatter と本文はすべて内容として扱う。**`sources[]` を bookkeeping 側に置くことが要である** — `action: update` はほぼ必ずソースを追記するため、それを内容とみなすと本方針は「常に戻す」に潰れる。人間がレビューしたのは記述であり、同じ記述に裏づけが 1 件増えることはその判断を無効にしない。一方 `expires_at` は内容側に置く（Pass 4 がこれを他の主張と同様にソースとの照合対象にしている。Issue #279）。

**第 3 の状態（`reviewed-stale` 等）は導入しない** — 信頼ラダーに 3 つ目を持ち込むと `review_status`・追跡 Issue・`review-issue-close-sync.yml` の全部に分岐が要る（Issue #669 が `review.auto_merge` を実装せず削除した理由と同じ）。**`wikicommit-merge` Step 8 も変更しない** — `pending` を走査する既存の挙動が、戻ったページを自動的に拾う。**既に陳腐化した `reviewed` を抱えた既存ページへの遡及適用も行わない**（新旧混在を許容する方針）。

`wikicommit-fix` が戻した場合、その場で `/wikicommit-review <page>` を実行すれば追跡 Issue のサイクルを待たずに再署名できる（経路 B はローカルに `reviewed` を書く）— 差分を読んだ本人が署名できる位置にいるため、この案内を Skill の報告に含める。

#### review_status 遷移

| ステータス | 意味 | 設定タイミング | Wiki ページの表示 |
|---|---|---|---|
| `pending` | **まだ誰も読んでいない**（このページの知識はまだ誰にも渡っていない）。品質チェックは通過済みであり、Pass 4 による出典との照合も済んでいる（Issue #750 / #751）— **欠けているのは到達であって、検査ではない** | `wikicommit-generate` 生成時に frontmatter へ埋め込み。**`reviewed` からの復帰もある** — `wikicommit-generate` の `action: update` / `--regenerate` / `wikicommit-fix` が内容を書き換えた場合、`reset_review_on_content_change.py` が `pending` に戻して `reviewed_by` を落とす（Issue #724。上記の節を参照） | ⚠️ LLM 生成であることを述べるバナー（読了に関する行は出ない。Issue #774 以前は「このページはまだ誰も読んでいません」という見出しが出ていた） |
| `reviewed` | **表明していること**（Issue #740）: このページを人が最後まで読んだ。すなわち**この Wiki の知識が、生成した機械以外の少なくとも 1 人に渡った**。読んで、報告すべきと感じたことは無かった。**表明していないこと**: 内容が正しいこと（出典との照合は Pass 4 が行い、その判定は `.wikicommit/review/` に記録され公開ページにも表示される。Issue #750 / #751）・網羅性（Issue #722）・世界が変わったが手元のどのソースも反映していない事実。**この定義は「見た」より一段強く、「保証した」より大きく弱い** — 単なる出席簿ではなく、知識が渡ったことを述べる | **経路 A**: レビュー追跡 Issue（`wikicommit-review` ラベル）を GitHub 上または `/wikicommit-review` から Close 後、`review-issue-close-sync.yml`（Issue #313）が `review_status` を書き換えて自動マージ<br>**経路 B**: `wikicommit-review` がローカルに書き込み → `wikicommit-merge` で自動マージ | 同じバナーに**読了の行が 1 行増える**（Issue #739 / #774。見出し・本文・生成情報は `pending` と同一のまま — レビューは行を足すのであって警告を取り消すのではない）。その行は経路 A では読んだ人の login、名前が無い場合は「人が読みました」（`review-issue-close-sync.yml` が Close した人の login を `reviewed_by` フロントマターに書き、`WikiCommitBanner` が表示する。Issue #663。経路 B とフィールドを持たない既存ページは名前なしの行を出す — 経路 B は `review_status: reviewed` を書く同じ呼び出しで `reviewed_by` を消すため、前回の経路 A のレビュアー名が新しいレビューの主として残ることはない（Issue #705）。[DesignDoc-data.md](DesignDoc-data.md) §4.1 の該当コールアウト参照） |

> **`review_status` は「出来事」の器であり、以前は「主張」を入れていた（Issue #740）**: 1 回の読みは 3 つの産物を同時に生み、**産物ごとに記録として取れる形が違う**。
>
> | 1 回の読みが生む産物 | 記録の形 | 行き先 |
> |---|---|---|
> | **(a) 欠陥への気づき** | **主張** — ページについて述べる。答えられるし反証もできる | giscus（確信なし。Issue #741）/ 報告 Issue（確信あり。Issue #738） |
> | **(b) 受け取った知識** | **出来事** — 起きたか、まだか。ページを調べても真偽が決まらない | **`review_status`**（Close） |
> | **(c) 価値の判断** | **量** — 集約して初めて意味を持つ | giscus（Issue #741） |
>
> `review_status` は 2 値のフィールドであり、**構造的に「出来事」の器である**。そこに (a) の「主張」を入れていたことが歪みの正体だった — 主張は内容を持つので 2 値には収まらず、内容を**外付け**する必要が生じ、それがチェックリストになった。そしてチェックリストが「保証」の形を採った時点で、Close は署名になった。**本 Issue がやったのは、器の形に合う産物を入れ直すことである**（レビューの意味を別のものに取り替えたのではない）。入れ直せばチェックリストは外付けである必要がなくなり、(a) は本来の居場所へ移る。
>
> **どこにも「これはレビューではない」とは書かない**。3 つの産物はすべて 1 回のレビューが生んだものであり、レビューという語はその全体を覆っている。分かれているのは産物と記録の形だけである。したがって語彙は Issue #583 が "ingest" について採った線をそのまま踏襲する — **表示文字列と定義文だけを変え、`review_status` / `reviewed_by` / `wikicommit-review` ラベル / ワークフローのファイル名 / Skill 名 / `Reviewed-by:` トレーラーは据え置く**。とくに `wikicommit-review` ラベルは既存の open な追跡 Issue に付与済みであり、改名すると重複判定（`--label wikicommit-review --state open`）が外れて**全ページ分が重複起票される**（Issue #583 が `<!-- wikicommit-ingest: -->` を据え置いた理由と壊れ方まで同一）。
>
> **(a) と (b) は選択肢ではない — 同じ行為が常に両方を生む**。Bacchelli & Bird, "Expectations, outcomes, and challenges of modern code review", ICSE 2013（DOI `10.1109/ICSE.2013.6606617`）の abstract は "reviews are less about defects than expected and instead provide additional benefits such as knowledge transfer" と "code and change understanding is the key aspect of code reviewing" の 2 点を述べている。**論文は「知識の伝播のほうが欠陥検出より大きい」とは言っていない**（"additional benefits" であり量的な比較はしていない）ため、本 Issue の主張はそこに依存しない — 依存するのは「1 回の読みが (a) と (b) を同時に生む」ことだけで、これは上記 2 つの引用が直接支えている。Wiki で (b) を記録すべき理由は 2 つ: **成果物が知識であり、知られていなければ存在しないのと同じである**こと、そして**機械は (a) はできるが (b) は原理的にできない**こと（機械がページをレビューしても、誰にも知識は渡らない）。
>
> **本 Issue は Issue #663 / #723 の副作用を引き受けるものであり、両者を誤りとして巻き戻すものではない**。#663 はバッジに名前を付け（「単なるフラグに見える」を直すため）、その結果 Close が署名になった。#723 は常に PASS する項目を削り判断を要する項目に置き換え、その結果 1 件あたりの重さが上がった。どちらも意味を強くする方向として正しく、**どちらもスループットへの影響を評価していなかった**。同時に本 Issue は **#723 の原理（機械が原理的にできないことを人に割り当てる）の延長**でもある — その原理を最後まで適用した答えが (b) であり、#723 が選んだ 2 項目（害・外部知識との食い違い）は機械が**苦手**ではあっても原理的に不可能ではない。#723 が半歩手前で止まったところまで、同じ原理を進めたのが本 Issue である。
>
> **「未レビュー N 件」の意味も変わる**。旧: 未検証の負債が N 件。新: **全数が出典と照合済みで、そのうち N 枚がまだ誰にも読まれていない**（Issue #751 が機械側の照合を表示するようになったことで、この読みが初めて成立する）。後者はページの欠陥ではなく**到達の状態**であり、恥じるものではない。
>
> **第 3 の状態は増やさない**（Issue #669 の懸念に当たらない）。新しい定義では **2 値であることの理由が構造から出る** — (b) は出来事なので「起きたか / まだか」の 2 値であり、量が要るのは (c) で、そちらは giscus が累積する。`reset_review_on_content_change.py`（Issue #724）も新しい定義で**最も自然に読める**（ページが変わったなら、渡ったものはもうそこに無い）。

### 6.4 翻訳パイプライン

翻訳パイプラインは「誰が・いつ呼ぶか（無人トリガー vs 対話実行）」と「1ページあたりの処理内容（原文全文 + 用語集注入 → 翻訳生成 → 品質チェック → フィールド付与）」を分けて考える。後者は呼び出し元によらず共通であり、**Phase 3 では対話実行版（`/wikicommit-translate`）を、Phase 4 では無人トリガー版を提供する**（Issue #280。詳細は下記）。

> **用語集を先に確定させてから本文を訳す（Issue #554）**: 呼び出し元によらず、**`DefinedTerm` 型のページを他の型より先に翻訳する**。無人トリガー版・対話実行版の一括モードとも、処理対象の並べ替えでこれを実現する（対話実行版の1ページ単体モードには並べ替える作業リストが無いため、この順序制御は効かない — 下記）。
>
> **注入する用語集は 2 つの異なるものからなる**。(a) 原語の `DefinedTerm` ページ全文 — その用語が**何を意味するか**を伝える。(b) 原語↔訳語の対応表 — その用語を対象言語で**どう書くか**を伝える。当初は (a) しか無く、訳語は各ページの翻訳時にその都度導出されていた。つまり同じ用語の訳が複数ページで一致することは「LLM が毎回同じ訳を選ぶ」ことにのみ依存しており、`DefinedTerm` は Wiki 内で最も他ページから参照される型であるため、揺れたときの影響範囲が最も広い型でもあった。
>
> **対応表は `title` だけを読む**。必要なのは原語ページと訳語ページの `title` の対であり（ファイル名＝slug が言語中立なので、basename がそのまま結合キーになる）、両言語の `DefinedTerm` ページを毎ページごとに全文読み込むと「ページ数 × 用語数」のコンテキスト消費になる（`dev/pilot-ai-driven-dev-wiki-round5.md` では `DefinedTerm` が 43 ページあった）。この抽出は毎ペアごとに実行するため、一括モードの実行中は用語集が確定するにつれて対応表が育ち、後続のペアがそれを見る。
>
> **品質チェックの突き合わせ対象にも対応表を加える**。従来の品質チェックは原語の用語集しか見ていなかったため、意味のずれは検出できても**訳語の不一致そのものは検出できなかった**（既に訳された他ページとの整合を見る材料が無かった）。対応表があれば、訳語の選択は LLM の判断ではなく客観的な参照先を持つ。ただし対象言語に `DefinedTerm` ページが実在する用語に限り適用され、`translator_notes`（Issue #524。そのページに対する人間の明示的な判断）が対応表（既定値）に優先する。
>
> **単体モードと、最初の `DefinedTerm` ページは対応表を持たない**（あるいは部分的にしか持たない）。これは不具合ではなく順序の帰結であり、対応表が空なら単にこの入力が何も寄与しないだけで、従来と同じ挙動に戻る。`DefinedTerm` ページ自身を訳す際も、兄弟の用語については対応表が使える一方、そのページ自身の用語は対応表から明示的に除外する — 既に翻訳が存在する（＝ `STALE` の）`DefinedTerm` ページでは、対象言語ディレクトリの走査がそのページ自身の**旧訳**を拾ってしまうため。除外しないと、この実行が「既存の翻訳を一切読まない完全ブラインドな再翻訳である」という前提（Issue #524 の `translator_notes` が唯一の例外）が崩れるうえ、品質チェックが旧訳との不一致を「直すべき問題」と判定するため、原語 `title` を修正しても訳語が永久に旧訳へ引き戻される。

#### Phase 4: 無人トリガー版（`main` マージが起点）

> **MVP（Phase 1–3）スコープ外。** main マージをトリガーに人間の介在なしで LLM を呼ぶ無人実行が前提となる一方、Phase 1–3 の Skills はすべて Claude Code 上での対話的実行（人間が `/wikicommit-xxx` を叩く）を前提としており、無人実行の仕組みを持たない。無人実行を可能にする `claude-code-action`（GitHub Actions 上で SKILL.md をそのまま実行）は Phase 4 の SaaS 実行基盤で導入されるため、無人トリガー版はそれに合わせて Phase 4 に据え置く（当時の計画は `dev/roadmap-phase4-5.md` にある。同ファイルは公開対象外 — `docs/README.md` §3）。

#### Phase 3: 対話実行版（`/wikicommit-translate`）

```
確認なしで全件を1ページ単体モードと同じ処理で順次実行
```

`--lang` 未指定時、`config.yml` の `translation.targets` が空配列の場合はエラー終了し、「対象言語がありません。`--lang <lang>` を指定するか `config.yml` の `targets` を設定してください」と案内する。

出力はローカル書き出しのみ。コミット・PR 作成は行わず、ユーザーが別途 `/wikicommit-merge` を呼ぶ（`wikicommit-generate` / `wikicommit-review` と同じ「対話実行・ローカル書き出しのみ」パターン）。

#### 翻訳の鮮度チェック・未翻訳検出

```
/wikicommit-status（または check_translation_status.py の定期実行）
  ↓
翻訳ページの source_commit と親ページの現 HEAD を比較 → ミスマッチで STALE
原文ページ × config.yml の targets の組み合わせで翻訳ページの有無を確認 → 存在しなければ UNTRANSLATED
  ↓
warning を表示（STALE は再翻訳、UNTRANSLATED は `/wikicommit-translate` の実行を提案）
```

#### WikiLink のクロス言語フォールバック

```
.wikicommit/entity/en/ ページ内の [[Person/yamada-taro]] の解決順序:
  1. .wikicommit/entity/en/Person/yamada-taro.md  → あれば使う
  2. .wikicommit/entity/ja/Person/yamada-taro.md  → translated_from を辿った親言語
  3. どの言語にも存在しない → 品質チェックが blocking エラー

翻訳ページが未作成 → warning のみ（非ブロッキング）
```

このフォールバックロジックはビルド前変換スクリプトと `wikicommit-ask` Skill の両方に実装する（Phase 5 以降のホスト型 MCP でも同ロジックを再利用する）。

### 6.5 削除フロー

```
/wikicommit-remove <page>
  ↓
対象ページに status: removed / removed_at / removed_reason を付与（ローカル変更）
├─ translated_from で紐づく翻訳ページも同様に処理
└─ 影響を受けた Type ディレクトリの index.md から該当エントリを削除
  ↓
/wikicommit-merge → 品質チェック → PR 作成
  ↓ 参照切れ WikiLink を検出 → 警告（非ブロッキング）
PR マージ → 公開 Wiki から非表示（ファイルは残る）
  ↓
（任意）/wikicommit-cleanup-links で参照切れ修正 PR を作成
（任意）ハード削除 PR を別途作成
```

> **`status: removed` ページは `content/` へビルドされない契約**（Issue #271）: 「公開 Wiki から非表示」とは、他ページからのリンク・索引（sources index・root index）から除外されるだけでなく、ページ自身も Quartz ビルドの入力である `content/`（`convert_wikilinks.py --output`）へ一切書き出されないことを意味する。書き出されてしまうと直接 URL でアクセス可能な状態のまま公開サイトに残ってしまう（`childcare-procedures-wiki` パイロットで実際に確認）。`convert_wikilinks.py` の `main()` は変換ループで `status: removed` のファイルをスキップし、さらに前回実行時に書き出された `content/` 内の `.md` のうち今回の実行で再生成されなかったもの（`status: removed` への変更・ソースファイル削除・リネーム等）を実行のたびに削除する（stale cleanup）。CI は毎回フレッシュチェックアウトのため通常 `content/` は空だが、ローカルで `npm run preview` を繰り返す場合にこの stale cleanup が効く。

### 6.7 Git コミットトレーラー規約

コミット author は常に人間ユーザー（Claude Code の実行者）となる。LLM の関与はトレーラーで記録する。

```
Co-Authored-By: <Claude display name> <noreply@anthropic.com>  # LLM が生成（GitHub 標準形式）
Generated-By:   <current model ID>                             # 生成モデルの精密なバージョン追跡
Reviewed-By-AI: <current model ID>                             # LLM がレビューした場合
Signed-off-by:  Taro Yamada <taro@users.noreply.github.com>    # 人間が承認（人間のみで作業した場合。CONTRIBUTING.md 参照）
Reviewed-by:    Taro Yamada <taro@users.noreply.github.com>    # レビュー追跡Issueを Close した人（経路A、Issue #313）
```

> **`<current model ID>` / `<Claude display name>` は穴埋め対象であり、サンプルのリテラルではない（Issue #559）**: 上の 1〜3 行目（`Co-Authored-By` の表示名と `Generated-By` / `Reviewed-By-AI` のモデル ID）は、そのコミットを作った実行中のモデル自身の値で置き換える。当初この規約は `claude-sonnet-4-6` というリテラルをそのまま書いており、Skill 側（`wikicommit-merge` / `wikicommit-schema-propose` の Step 5）もそれをヒアドキュメントに埋め込んでいたため、**別のモデルで実行しても常に Sonnet 4.6 と記録される**状態になっていた（`dev/pilot-decameron-wiki.md` で実地確認）。`Generated-By` の目的は本節自身が述べるとおり「生成モデルの精密なバージョン追跡」であり、固定値ではその目的を果たさない。さらに悪いことに、同じコミットが変更しているページの `generated_by` フロントマター（`wikicommit-generate` Pass 3 が実行中のモデル ID を書く）とトレーラーが食い違うという自己矛盾したコミットが日常的に作られていた。「監査・ロールバック・バックアップはすべて `git log` で完結する」（CLAUDE.md）という GitOps の主張を、`git log` 上のモデル情報が実態と一致しないことで直接損なう。
>
> **`Generated-By` / `Reviewed-By-AI`（モデル ID）**: `generated_by` / `translated_by` フロントマターと同じ自己申告の値を使う。ランタイムが報告する文字列をそのまま書き、接尾辞を落としたり短縮・正規化したりしない — `wikicommit/saitama-city-wiki` では同一リポジトリ内の `generated_by` に `claude-opus-5[1m]` 79件 / `claude-opus-5` 4件という表記ゆれが実際に発生している。取りうる値の正規化表（モデル ID のレジストリ）を WikiCommit 側に持つ案は採らない — 新しいモデルが出るたびに更新が要り、更新が漏れた瞬間に「表に無い ＝ 不正な値」になってしまうため。ゆれの防止は「ランタイムの報告どおりに書く」という単一の規則で行い、機械検証は課さない（`validate_frontmatter.py` は `generated_by` を空文字列でないことしか検証しない）
>
> **`Co-Authored-By`（表示名）**: 実行中のモデルの人間可読な表示名を書く。確信を持って分からない場合は素の `Claude` と書く。GitHub の共同作成者リンクはメールアドレス（`noreply@anthropic.com`。こちらは固定のリテラル）で解決され表示名では解決されないため、保守的な `Claude` に落としても失うものは無い一方、当て推量の表示名は GitHub の UI 上で実際には関与していないモデルを共同作成者として表示してしまう。表示名を完全に諦めて常に `Claude` 固定にする案（Issue #559 の対応方針 3）も検討したが、表示名を知っているモデルからその情報を捨てる理由が無いため、「知っていれば書く・不確かなら `Claude`」という条件付きの形にした
>
> **レビュー追跡 Issue（`wikicommit-review` ラベル）の `Reviewed-by` は Issue Close 時に Action が自動生成する（Issue #313。旧 Issue #281 の `Signed-off-by` 自動生成を置き換え）**: `.github/workflows/review-issue-close-sync.yml` が `issues.closed`（ラベルが `wikicommit-review`）イベント発火後に `gh api repos/{owner}/{repo}/issues/{number}` でライブ再取得した `closed_by.login`（Issue #403 — イベントペイロードのスナップショット値 `github.event.issue.closed_by.login` は本リポジトリでは常に空文字列で返ることが実地検証で判明し、ライブ再取得方式に変更した）から得た GitHub 認証済みの Close 実行者アカウントを元に `Reviewed-by: <表示名> <<login>@users.noreply.github.com>` を組み立て、`review_status` を `reviewed` に書き換えるコミットに埋め込む。人間が手入力するトレーラーではなく、書き忘れ・入力ミス・なりすましを避けるため機械的に生成する。トレーラー名を `Signed-off-by` ではなく `Reviewed-by` にしたのは、DCO（Developer Certificate of Origin）等で使われる `Signed-off-by` の一般的な意味（変更内容そのものへの法的な保証）と、ここでの実際の行為（ページ内容を読んでレビュー完了とみなした）を区別するため。対象はレビュー追跡 Issue の Close イベントのみで、経路Aの一括PR・経路B（`wikicommit-review` がローカルで人間自身のセッションとして実行するケース）は対象外（詳細は §6.2 参照）。
>
> **`Reviewed-by` トレーラーの改ざん耐性の範囲**（`ai-driven-dev-wiki` PR #53 の実地確認に基づく整理）: この仕組みは「誰が Issue を Close したか」と「その事実がコミットにどう反映されるか」で信頼性の性質が異なる二段構えになっている。前段（`closed_by` の取得）は GitHub サーバー側の認証に基づく事実であり、Issue への書き込み（Close）権限を持たない第三者には偽装できない — Close できるのは Issue 作成者かリポジトリの書き込み（triage 以上）権限保持者のみで、これは GitHub 自身が強制する。後段（取得した値を `Reviewed-by:` としてコミットメッセージに書き込む処理）は git・GitHub いずれも内容を検証しないただの自由記述テキストであり、加えてこのコミット自体も GPG/SSH 署名を行っていない（`ai-driven-dev-wiki` PR #53 のコミットで `verification.verified: false` を確認済み）。したがって、リポジトリへの書き込み権限を持つ人物であれば、本ワークフローを経由せず直接同内容のトレーラーを含むコミットを push することも技術的には可能である。ただしこれは「その人物が元々持つ書き込み権限の範囲内でできること」であり、前段の GitHub 認証そのものを迂回する攻撃ではない（書き込み権限を持つ人物は、そもそもトレーラーを偽造するよりページ内容を直接改ざんする方が容易であり、実害の起点は結局リポジトリの権限管理に帰着する）。より強い保証（コミット自体の非改ざん性）が必要な場合は branch protection の "Require signed commits" が候補になるが、private リポジトリでは GitHub Free プランでは利用できず（public 化または GitHub Pro が前提）、有効化した場合は本ワークフロー・`wikicommit-merge` の bot コミットが軒並み unsigned のため別途署名基盤の整備が必要になる。現時点では対応不要と判断し、将来 Phase での検討課題として記録するに留める。
>
> **`closed_by` が空になる理由と `sender` という代替候補**（`ai-driven-dev-wiki` での実地検証、2026-08-05）: GitHub 公式ドキュメント上、`closed_by` は `GET /repos/{owner}/{repo}/issues/{issue_number}`（単一 Issue 取得エンドポイント）のレスポンススキーマとしてのみ定義されている。GitHub Community での報告（[Discussion #136301](https://github.com/orgs/community/discussions/136301)）によれば、この `closed_by` は「List repository issues」（一覧取得エンドポイント）のレスポンスには含まれないという既知の非対称があり、GitHub からの公式な説明はない。Issue #403 が実地で踏んだ `issues.closed` webhook ペイロード内 `issue.closed_by` の欠落は、この非対称パターンの webhook 版とみられる（webhook ペイロードに埋め込まれる `issue` オブジェクトは一覧取得に近いスナップショットで、単一 Issue 取得時のみ計算される値が省かれる）が、webhook ペイロードのケースを名指しで扱った公式ドキュメントは見つからなかった。
>
> この整理と並行して、`issues` webhook ペイロードのトップレベルには `sender`（"the user that triggered the event"）という別フィールドが公式に文書化されており存在する。`review-issue-close-sync.yml` に一時的なデバッグステップを追加し、実際に `ai-driven-dev-wiki` でテスト用 Issue を Close して確認したところ、`github.event.sender.login` は Close 実行者（`joyk0117`）を正しく返し、同時に `github.event.issue.closed_by`（生値）は `null` だった — Issue #403 の実地確認結果を追試する形で再確認できた。デバッグステップは検証後に revert 済み、検証用 Issue も削除済みで、本番の自動マージパイプラインには影響していない。`sender` を使えば `gh api repos/.../issues/{number}` によるライブ再取得（および付随する `issues: read` 権限）を省略できる可能性があるが、公式ドキュメントは「GitHub がイベントの実行者を特定できない場合 `sender` が "ghost" ユーザーに解決されることがある」と注記しており、この置き換えを行うかどうかは別途検討する（`Issues/p3-166-review-issue-close-sync-sender-vs-closed-by.md` として草案化（非公開の開発リポジトリ側の記録））。

## 7. 品質ゲート — 概要

### チェック種別と実行主体

| レイヤー | チェック内容 | 実行者 |

| 構造 | スキーマ適合・sources フィールド存在 | `wikicommit-merge`（`validate_frontmatter.py` を呼び出し） |
| WikiLink | WikiLink 参照先存在確認・removed ページへのリンク検出・Type セグメント取り違え検出（Issue #563） | `wikicommit-merge`（`check_wikilinks.py` を呼び出し） |

| 内容 | 元文書との整合性・ソース間の食い違い・**WikiLink 1ホップ以内の**ページ間矛盾検出（Issue #566）。**判定は `.wikicommit/review/` に記録される**（Issue #750 — PASS したページと `failed_pages` に落ちたページの両方） | `wikicommit-generate` の生成エージェントループ内（ユーザー自身の LLM 契約で実行） |
| 内容 | 合成ページ（view ページ）と grounding ページ群の照合（裏付けの無い主張の検出・grounding ページ同士の食い違いの報告。Issue #674）、および `kind` の `Boundary` 検査（Issue #675 — 検査が無ければ `kind` は誰も見ないラベルになって drift する） | `wikicommit-synthesize` Step 5.5 のレビューサブエージェント（同上） |

> **検査の内容は `.wikicommit/review-rules.md` にある（Issue #752）**: 上表の「内容」2 行が指す検査項目は、以前は 3 つの SKILL.md に書き分けられており、**既に食い違っていた**。現在は 1 ファイルにまとまり、「全経路共通の規律」と「経路ごとの差分」が構造的に分かれている。**検査の内容自体は変わっていない** — 移動と食い違いの解消であり、規律を足しも引きもしていない（3 箇所の食い違いを揃えた分だけ、弱い側が強い側に揃う）。段取り（リトライ・`failed_pages`・書き出し・`status` 更新）は各 Skill に残っている。
>
> **判定が記録されるようになった（Issue #750）**: 上表の「内容」2 行が掛ける検査は、以前はどのページについても結果が残らなかった — Pass 4 の返す JSON は「ディスクにも Git にも残さない」と定義されており（`docs/DesignDoc-data.md` §4.6）、**1 回目で通ったページと 2 回目で通ったページがディスク上で同一に見えた**。残るのは `failed_pages`（＝一度も書き出されなかったページ）だけで、これは「レビューが機能した記録」ではなく「レビューが救えなかった記録」である。
>
> 現在は `record_review.py` が §4.6 の JSON から `source_quote` を落として射影したものを `.wikicommit/review/**/*.md` に書き、`check_review_coverage.py` が読み戻す（§4.8）。**品質ゲートの判定自体は何も変わっていない** — ブロックする条件も FAIL の定義も同じで、変わったのは判定が残るかどうかだけである。
>
> これにより上表の「全ページに掛かる」という主張が初めて検証可能になる。**同時に、機械レビューが評価しないもの（下記）の範囲も変わらない** — 記録されるのは実際に下した判定であって、網羅性でも害でもない。
>
> **「ページ間矛盾検出」の実装範囲（Issue #566）**: 上表のこの欄は当初「元文書との整合性・ページ間矛盾検出」と書かれていたが、**Pass 4 の実装は 1 ページ × そのページ自身の `sources` の照合しか行っておらず、他のページを見る手順はどこにも存在しなかった**。設計表に書かれた責務に対して実装が無い状態であり、そのまま OSS 公開すれば実装されていない保証を謳うことになる。`dev/pilot-saitama-wiki.md` では別セッションの 4 体のレビューエージェントが原典と文字列レベルで照合した結果、ハルシネーション・捏造・誤帰属・孫引き出典・年号誤りは 1 件も検出されなかった一方で、ページ同士が食い違う事例が 3 件公開まで到達していた（各ページは個別には出典に完全に忠実であり、Pass 4 は正しく機能していた — 機能していなかったのは突き合わせだけである）。
>
> Issue #566 は表の記述を削るのではなく実装する側を採り、**照合範囲を明示する形で欄を書き換えた**。実装したのは 2 つ:
>
> - **ソース間の食い違い**（同一ページ・複数ソース）: ページが 2 件以上の `sources` を持つとき、それぞれと矛盾しないかを個別に見るだけでは足りない。ソース同士が食い違っているとき、**その事実の主題をその文書自身の主題として扱っている方**を採る（一覧・目録・名簿の類は、その項目を主題とする文書より弱い証拠）。saitama では、市全体の企業一覧の 1 行（他の項目はすべて正しく、誤りはその 1 件のみ）を無検証で採用した結果、クラブの本社所在地が同一リポジトリ内の 2 ページと正面から矛盾していた。追加コンテキストを要さない（ソースは既に Pass 4 のコンテキストにある）ため最も費用対効果が高い
> - **WikiLink 1 ホップ以内のページ間矛盾**: レビューサブエージェントに、そのページが**既存のページ**へ張る WikiLink の参照先と、そのページを参照している既存ページを追加コンテキストとして渡す。**合計 5 件を上限**とし、outbound を先に取る（`wikicommit-ask` の 1 ホップ展開が採る上限と同じ桁。Issue #459）
>
> **検出時の扱いは、どちらのページが誤っているかで分岐する**。レビュー中のページが誤っている（自身のソースが相手側の記述を支持している）なら通常どおり FAIL して再生成する。**相手側が誤っていそうなら FAIL にしない** — Pass 4 は 1 ページをそのページ自身のソースに対して再生成するループであり、相手ページのソースも持たなければ相手ページへの権限も持たない。Completion Notice にペアを列挙して報告するに留める。この向きが重要で、saitama の 3 件目は新規ページ側ではなく**既存の粗い記述側**が誤りだった。
>
> **2 つの限界を、解決せずに受け入れている**。同一バッチ内では、あるページは自分より**先に**生成された兄弟しか見られないため、ペアが片側からしか照合されない（あるいは全くされない）ことがある。異なるバッチで生成された 2 ページ間の矛盾は原理的に届かない。全ページ生成後にもう 1 周する案は採らなかった — バッチ内の順序依存は解消するが、バッチをまたぐ方は解消せず、コストだけが倍になるため。
>
> **リポジトリ全体走査は本 Issue の実装スコープ外**とし、将来の課題として記録する。実装するとすれば、`/wikicommit-synthesize` の俯瞰モード案と同じ機構になる — ページ群をチャンクに分割し、チャンクごとにサブエージェントを走らせて結果を統合する map-reduce であり、返却形式も `docs/DesignDoc-data.md` §4.6 のエージェント間 JSON をそのまま使える。分割戦略も共有できる: 無関係な 2 ページを突き合わせても矛盾は出ないため、リンククラスタ単位で分割すれば照合の当たりが良くなる（上記の WikiLink 1 ホップを、バッチ境界に依存しない形へ一般化したものと見なせる）。置き場所は独立した監査 Skill が有力で、`wikicommit-status` に足すのは避けたい — 同 Skill は現状すべて決定論的・読み取り専用スクリプトで構成されており（`check_ingest_freshness.py` の書き戻しを除く）、そこに LLM 走査モードを足すと性質の異なるものが混ざる。
>
> **saitama の 3 件がこの実装で検出されうるか**（Issue #566 の完了条件）: 浦和レッズ本社（同一ページ・複数ソース）は**ソース間の食い違い**が確実に拾う。見沼干拓の年（`Place/minuma` と `Place/minuma-tsusenbori`）は、両ページが互いを WikiLink で参照している限り 1 ホップで拾える（見沼通船堀のページが見沼へリンクしない可能性は低い）。県内最初の公園（`Place/tsukinomiya-park` と `Place/omiya-park`・`Place/hikawa-shrine`）は、後 2 者が隣接施設として相互にリンクしている一方、月の宮公園がそのどちらかへリンクしているかは確実でない — **リンクされていなければ 1 ホップでは届かず、上記の全体走査を待つことになる**。3 件中 2 件は確実、1 件はリンクグラフ次第、というのが正直な見積もりであり、実 LLM による再実行での確認は行っていない。
>
> **合成ページの照合は `wikicommit-synthesize` の中で行う（Issue #674）**: ページを書く 3 経路のうち、合成だけが検証を持たなかった。`wikicommit-generate` は Pass 4 で外部ソース文書と、`wikicommit-translate` は翻訳品質チェックで原文ページと照合する一方、`wikicommit-synthesize` は SKILL.md Step 5 の「grounding ページ本文に無い主張を書くな」という 1 文だけが防護であり、それを Issue #283 のスコープ判断として自ら明記していた。
>
> **合成ページは 3 経路の中で最も検証が要る側にある**。`sources` を持たず `derived_from` のみを持つため、読者が内容を確かめる唯一の道が grounding ページを辿ることであり、そこが誤っていれば追跡は不可能になる。とりわけ `MISSING_SOURCE`（どの grounding ページ本文にも裏付けが無い主張）は、**これを見る主体がパイプライン上どこにも存在しなかった**。
>
> 実装は Pass 4 と同型で、返却形式も §4.6 のエージェント間 JSON をそのまま使う（新形式を作らない）。`source_file` には grounding ページのパスが入る — Issue #566 が置いた「`.wikicommit/entity/` 配下のパスかどうかで何と矛盾しているかを判別する」規約にそのまま従う。FAIL 時は `issues[].instruction` を再生成プロンプトへ明示的に渡す（Issue #452 が Pass 4 で配線したのと同じ形。指示を渡さない再生成は同じ誤りを繰り返す）。
>
> **再試行回数は `generate.max_retries` を流用し、専用キーを新設しない** — 意味が同じ設定を 2 つ持つ理由が無い。**上限超過時は書き出さずに停止して報告する**: `wikicommit-generate` の `failed_pages` に相当する記録先が無い（合成ページはソース管理ファイルを持たず、`wikicommit-merge` Step 9 の生成失敗トラッキング Issue も `.wikicommit/source/` を走査対象とする）一方、1 回の実行で 1 ページしか書かないため「部分的な成功」という状態自体が存在せず、停止して報告すれば情報は失われない。
>
> **grounding ページ同士の食い違いは FAIL にしない**（`page_at_fault: "other"` と同じ扱い）。この Skill は grounding ページを書き換える権限を持たないため、FAIL にすると正しい合成を作り直しては同じ指摘を受けることを繰り返し、上限で捨てられる。完了報告にペアを列挙するに留める。
>
> **grounding set から二次ページ（`derived_from` を持つページ）を除外する**ことで「合成ページは通常ページの 1 段上にしかない」という不変条件が成立し、2 つが従う: (1) `check_derivation_freshness.py` が陳腐化を完全に捉えられる（合成の合成では、間のページが再生成・コミットされない限り伝播しない）、(2) 上記の照合が必ず `sources` を持つページに着地し、外部文書まで最大 2 ホップで辿れる。**索引からは除外しない** — 読者と `/wikicommit-search` / `/wikicommit-ask` が合成ページを見つけられなくなるため、除外するのは grounding set からのみである。
>
> あわせて、grounding のうち `review_status: pending` のページを本文生成の前に列挙して伝える（Issue #283 が未解決事項として残していた項目。文言は `wikicommit-ask` の ⚠️ と揃える）。**警告でありゲートではない** — 生成バッチ直後の Wiki は全ページが `pending` であり、そこで止めると最も有用な場面で Skill が使えなくなる。得られるのは「未レビューのページから未レビューのページができた」ことが黙って成立しなくなることで、出力の `review_status: pending` だけではレビュー済みの材料から作られたページと区別がつかない。

### 機械レビューが評価しないもの（Issue #722）

WikiCommit の機械レビューは「生成ページが与えられたソースに忠実か」を見るものであり、**網羅性**（他の資料を調べれば足せる情報があるか）は評価対象ではない。これは一貫して運用されてきた前提だが、**どこにも書かれていなかった** — 配布 Skill 全体を `completeness` / `comprehensive` で grep しても 0 件だった。証拠拘束ルール（Issue #442）は「ソースに書いていないことを書くな」という**過剰**の側だけを禁じており、「ソースに書いてあることを全部書け」を要求しないことは述べていない。

書かれていない前提は drift する（Issue #552・#571 が同じ形を繰り返し踏んでいる）。実害は 2 方向にある: レビュアーが網羅性を基準に読み始めると毎回 Web 検索が走ってレビューコストが増大し、「ソースにはあるがページに無い」がすべて欠陥に見えて `generate.max_retries` を消費し `failed_pages` に落ちる — 実際にはその大半は `granularity` による正当な取捨選択である。

**レビュー経路は 3 つある**（`wikicommit-generate` Pass 4・`wikicommit-review` Step 4・`wikicommit-synthesize` Step 5.5）。3 経路とも独立に配布される別 Skill であり、共通化しない方針は Issue #552 が確立している（短い文面は各自が持つ）ため、以下の 2 ルールは 3 箇所それぞれに書く。

| ルール | 内容 |
|---|---|
| **網羅性は基準ではない** | ソースが述べているのにページが書いていないことは、それ自体では欠陥ではない。何を書き何を書かないかは型テンプレートの `granularity` と Pass 3 の抽象度ルールが決めており、レビューはその判断を再評価しない。合成ページ側では「ソース」を grounding ページに読み替える |
| **外部調査は行わない** | 判断がつかないときに Web 検索・未登録文書の取得へ出ない。例外はソースの記述自体が疑わしくそれを確かめないとレビューが成立しない場合に限り、その旨を所見に明記する |

**「FAIL にしてよいのは、ソースに無いことをページが述べている場合に限る」という形で書いてはならない。** それは FAIL 条件の網羅列挙として読め、Pass 4 が現に持つ他の FAIL を弱める — 帰属の取り違え（Issue #429）・無帰属の単一ソース定式化（同）・ソース間の食い違いでページが弱い側を採った場合（Issue #566）は、いずれも主張の内容自体はソースに書いてあり「ソースに無いことを述べている」に当たらない。書くのは**不足の側だけを免責する非対称**であって、過剰の側の再定義ではない。

**外部調査の禁止は証拠拘束の言い直しではない**。判定に使える**証拠**の側は既に 3 経路すべてに書かれており、4 度目の言い換えを足すことは Issue #552 の「共通のルールを個別の場所で言い直さない」に反する（しかも `wikicommit-generate` SKILL.md は既に推奨 500 行の 2 倍あり、Skill 起動のたび全文がコンテキストに載る）。足すのは**行動**の側 — 証拠拘束は「自分の知識で判定するな」とは言うが「調べに行くな」とは言っていない。あわせて `wikicommit-review` Step 4 の WebFetch は**登録済み**ソースの再取得であって外部調査ではない、という区別を併記する（書かないと、同じ手順の中に「WebFetch を使え」と「外部調査するな」が並ぶ）。

#### `MISSING_SOURCE` は登録候補として拾う（Issue #722）

Pass 4 は Issue #451 / #473 により、ページが引用・言及している文書が `sources` に無い場合を `MISSING_SOURCE` として FAIL させる。しかし **FAIL → 再生成でその記述が落ちれば PASS になり、「どの文書が足りなかったか」はどこにも残らない**。Issue #315 が旧 `better_type_candidate` 方式について指摘した構造と同じで、判断は下されているのにそれを拾う経路が無い。しかも拾うのは容易である — その文書の URL / タイトルは Pass 4 のコンテキストに現に載っている（`source_quote` がそれを引用しているからこそ `MISSING_SOURCE` と判定できた）。

必要なのは網羅性チェックではなく「レビュー中に判明した、登録候補になりうる文書」の 1 行報告であり、`coverage_gap_note`（Issue #284）・`page_at_fault: "other"`・`ORPHAN` と同じ「報告するがブロックしない」形に収まる。登録は既存経路（`/wikicommit-generate <url>` → `action: update`）がそのまま担うため新機構は要らない。

- **収集は Pass 4 の各回で行う**（最後に残ったものを見ても何も残っていない）。step 5 が `failed_pages` について既に採っている running list の形をそのまま使い、出力は書き出し確定後に一度だけ・**文書単位に畳む**
- **URL が無い場合は特定可能なタイトルで報告し、どちらも無ければ報告しない**（「以前の投稿」としか辿れない主張には登録すべきものが無く、毎回出る 1 行は Issue #562 が警告した「常時点灯して読まれなくなる」側へ寄る）
- **`failed_pages` との二重報告を避ける**。あちらは**ページ**を、こちらは**文書**を報告する別々の対象なので、ある文書を挙げたページがすべて破棄された場合はその旨をその行に添える（読み手に 2 つの一覧を突き合わせさせない）
- **`wikicommit-synthesize` Step 5.5 の `MISSING_SOURCE` は対象外**。同じ enum 値だが意味が違う — あちらは「どの grounding ページもその主張を述べていない」ことを指し、指すべき外部文書が存在しないため `source_file` を空にする規約まで持つ（Issue #674）。同じ扱いにすると、登録すべき URL が無いところに「`/wikicommit-generate` で登録せよ」という空の勧めが出る
- **`wikicommit-review` Step 4 も同じ判定を持つが、形は違う**。あちらは再生成ループを持たず人間が読む所見を出すだけなので、running list もロールアップも要らず所見 1 件として報告する。突き合わせ先は**ページの `sources` フィールドそのものではなく Step 4 手順 1 が実際に集めたソース集合**とする — 翻訳ページは `sources` を持たず親から継承する設計（[DesignDoc-data.md](DesignDoc-data.md) §4.2）であり、フィールドを直接読むと翻訳元を含む全文書が登録候補として挙がる。`derived_from` ページは上記の synthesize と同じ理由で対象外

**網羅性を機械的に検出する仕組みは作らない**。「ソースにあってページに無い」を数える手段は原理的にレビューと同じコストがかかり、しかもその差分の大半は `granularity` による正当な取捨選択である。**既存ページへの遡及適用も行わない**（新旧混在を許容する方針）。

### orphan 検出の設計

| 操作 | 挙動 |
|---|---|
| 削除フロー（status: removed 付与） | 参照切れを **warning のみ**（マージ可） |
| 新規追加 | `status: removed` なページへの WikiLink を **ブロック** |
| 新規追加（参照先ページがどの言語にも存在しない） | **warning のみ**（常にマージ可。Issue #340 — 旧ブロック。集計は `check_wanted_pages.py` が別途担う） |
| 新規追加（参照先ページは無いが、同じ slug が別 Type に実在する） | **ブロック**（Issue #563。実体は在り正しい対処はリンク 1 語の修正であるため、#340 の「WikiLink 化をやめて地の文で書く」という回避行動が成立しない。ERROR メッセージが実在する Type を名指しする） |
| orphan（被リンクゼロ）ページ | **warning のみ**（常にマージ可） |
| wanted（被参照だが実体なし）ページ | **warning のみ**（常にマージ可。`wikicommit-status` の `check_wanted_pages.py` が全ページ横断で集計。Issue #340） |
| 重複ページ | **ブロック** |
